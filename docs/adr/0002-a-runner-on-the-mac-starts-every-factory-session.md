# A runner on the Mac starts every factory session

Flight Deck ships a program as well as skills. One runner per Mac, kept alive by launchd, polls Linear and GitHub about once a minute and starts every factory session as a `claude -p` run of the unmodified Claude Code binary. One runner serves every repo on the Mac with a factory, because those repos share one Claude plan's limits. In v1, each repo's factory runs on one Mac, because two runners on one team would take the same issue (ADR 0017). Taking issues, the concurrency cap, worktrees, and recovery from failed sessions are code in the runner, not instructions in a prompt.

## Considered options

- **The board's routines, as one launchd job per flow.** Flight Deck would ship only skills and plists. An issue would wait up to an hour between stages. Every tick would spend a session from the plan limits just to look for work. The rules for taking issues and for recovery would live in prompt text that a session can ignore.
- **Claude Code's own schedulers.** Desktop scheduled tasks need the app open. `/loop` needs an open session and expires after 7 days. `claude --bg` is a research preview that needs an interactive trust step for each folder. None of them starts a session when an issue changes in Linear.
- **An Agent SDK program instead of `claude -p`.** It adds a permission callback and typed events. Anthropic's terms tell products built on the Agent SDK to use API keys, so the SDK would rule out running the factory on the maintainer's subscription.

## Consequences

- Factory sessions load the repo's own Claude Code files and Flight Deck, and nothing from the maintainer's user setup. The runner passes `--setting-sources project,local`, then adds Flight Deck back with `--plugin-dir` and the Linear MCP server with `--mcp-config`. A maintainer's personal `CLAUDE.md` rules, such as using GitButler, never reach a factory session. ADR 0007 narrows the flag to `--setting-sources ""`, which loads no settings file, loads the repo's instructions through `--add-dir`, and locks what each session loads. Neither flag keeps out the maintainer's `~/.claude/CLAUDE.md` or shell startup file, so ADR 0007 excludes both.
- The runner starts each session as `claude -p "/flight-build FLD-123"` with `--output-format stream-json --verbose` and a `--session-id` it picks, so it can find the transcript. On an API key, it adds `--max-budget-usd` (ADR 0007).
- Installing Flight Deck means installing the runner and its launchd agent. A Claude Code plugin can't do that on its own, because every process a plugin declares stops with its session. ADR 0024 points the agent at a launcher that never changes and adds a second agent for the menu bar app.
- The launchd agent sets `ProcessType` to `Standard`. macOS throttles the CPU and disk of a `Background` job and of every process it starts. Under `Background`, Shaders' typecheck took 500 s in a session instead of 50 s, and six unit tests timed out.
- While any session runs, the runner holds `caffeinate -i`, so idle sleep can't stop a session. A closed lid still stops the factory. Flight Deck schedules no wakes and needs no root access.
- Each poll reads Linear with filtered GraphQL queries, never one query per issue. The Flight Deck app user gets 5,000 requests and 2,000,000 complexity points an hour, shared by every factory in the workspace. One query may cost at most 10,000 points, and a request over a limit fails with `RATELIMITED`.
- At most 2 sessions run at once across the Mac's repos, and the maintainer can change the cap in `~/.config/flight-deck/config.toml`. When more work waits than the cap allows, the runner starts check first, then build, then plan. Within a stage, it orders issues by Linear priority, then by how many issues each one unblocks, then by age.
- To take an issue, the runner moves it to its stage's working status and adds the session to its session list, which holds the issue, the stage, the process, the session ID, and the worktree. A hand run makes the same move first. The runner skips any issue in a working status.
- An issue outside a spec waits in Ready to plan until every issue that blocks it has a `completed` status, so plan never writes a brief against code a blocker is about to change. A blocker in Landed doesn't count, because its code is on a spec branch, not the default branch. A blocker marked a duplicate counts as the issue it duplicates. A canceled blocker, or a duplicate with no original, pauses the issue (ADR 0004). The runner tests blockers only at plan's take. A blocker the maintainer adds after plan has written the brief is theirs to act on: they send the issue back to Ready to plan, and plan writes a new brief once the blocker is Done. A waiting issue stays out of the order above, and the runner writes nothing in Linear about it. Linear already marks a blocked issue, and `flight-deck status` lists each waiting issue with its open blockers and their statuses.
- The runner makes a fresh worktree for every session and deletes it when the session exits. Plan's starts at the default branch, or at the spec branch's tip for a sub-issue (ADR 0004). Build's starts on the issue branch, and check's at the commit it judges. The runner never passes `--worktree`, because a `-p` run leaves that worktree behind.
- A session that exits before its stage's handoff has failed. The runner restarts the stage once, in a fresh session that starts from what the failed one wrote, never from its transcript. A second failure pauses the issue with a comment that names the stage, the exit, and the transcript path. A Linear write that fails during the apply for a network error, a 5xx, or `RATELIMITED` isn't a failed stage, because the session handed off: the runner keeps the outbox and retries the apply with backoff, with no session, and pauses the issue only after 3 hours (ADR 0019).
- A clean logout or shutdown sends the runner SIGTERM, and it stops its sessions and puts their issues back in their queues without using the retry. After a crash or a power loss, the runner treats every session in its session list with no live process as failed, unless the session's exit was recorded before the old runner stopped, in which case it applies the outbox. A take the list doesn't hold, such as a hand run, stays as it is. Past the stage's time limit, which the repo record sets, the runner flags that issue as a stale take (ADR 0011).
- On a subscription, the runner holds itself once usage reaches 80% of the five-hour window or 70% of the weekly one, and the maintainer can change both in `config.toml`. It reads usage from the latest `rate_limit_event`, which every `stream-json` run emits with the five-hour and seven-day `utilization` and `resetsAt`.
- A session that hits a plan limit ends, and its output shows a `rate_limit` error or a `rate_limit_event` whose `status` is `rejected`. The runner doesn't count that exit as a failure. It holds itself until the event's `resetsAt`, then restarts the stage fresh without using up the stage's retry. The runner never sets `CLAUDE_CODE_RETRY_WATCHDOG=1`, which would make the session wait out the window instead.
