# A change request amends the brief, and a GitHub review can send work back

The maintainer starts review from the "Needs your review" flag in Linear and reads the diff on GitHub (ADR 0020). GitHub is where a reviewer comments on a line, but build reads only Linear and its inbox, and nothing carried the maintainer's GitHub comments to either. A maintainer who reviewed the diff there had to copy each comment into Linear by hand. So the runner now carries them. A Request changes review from the maintainer, on an issue in In Review, moves the issue to Ready to build at the runner's next poll. A move in Linear still works, and the runner carries the same comments. Comment and Approve reviews move nothing. Each thing the maintainer asks of a change after check passed it, in a GitHub review or a Linear comment, is a change request. A change request amends the brief for that issue: build does what it asks, and check judges whether build did.

## Considered options

- **Only a Linear move sends work back.** The runner would still carry the comments, but the maintainer would submit a review and then move the issue: two writes for one decision. ADR 0019 cut a pause's answer to one write for the same reason.
- **Any submitted review with a comment sends work back.** A PR the maintainer meant to approve with one nit would go back to build. Request changes is the review that already means "not yet".
- **A change request works like a finding.** Build could dispute it, and check would drop or repeat it. An agent would overrule the one person who can change the brief.
- **A change request goes back to plan,** which rewrites the brief before build runs. A plan session would run for "rename this". A maintainer who thinks the brief itself is wrong still moves the issue to Ready to plan, and plan reads the same comments.
- **The comments reach build only through its inbox.** Sessions read the inbox as untrusted text, and debrief reads each issue's history in Linear, where the comments would be missing.
- **Anyone with write access counts as the maintainer.** GitHub's `author_association` calls the machine user a COLLABORATOR, and on an org repo it calls every member one.
- **The maintainer resolves their own threads.** An unresolved thread carries to the next build, so a thread build already fixed would reach build again unless the maintainer resolved it by hand.

## Consequences

- Setup reads the maintainer's GitHub login from their own `gh` session and records it in the repo record. The runner carries only comments whose author has that login. It never carries or replies to anyone else's comment, whether a stranger's or a collaborator's. To have one acted on, the maintainer quotes it in their own review.
- GitHub hides a pending review's comments until the reviewer submits it, so the runner never sees half a review.
- The runner carries every unresolved thread the maintainer started, from any review. It also carries every review body and top-level comment the maintainer posted since it last carried their comments, because those can't be resolved. A thread from an earlier Comment review counts, and a resolved thread drops out. Comments posted after the merge reach nobody.
- The runner gains one move of its own: from In Review to Ready to build, on a Request changes review from the maintainer. Its code enforces the move with the rest of the lifecycle (ADR 0007). When check passes an issue, the runner first looks for a Request changes review that the maintainer submitted since the runner last carried their comments. If it finds one, it sends the issue to Ready to build instead of flagging. The maintainer never gets the "Needs your review" flag on a change that hasn't seen what they already said. When a verdict, or a conflict with the default branch, sends work back to build, the runner looks too. If it finds one, it carries the maintainer's comments in the same round, so build reads them beside check's findings instead of one round later. That send-back is the maintainer's as well, so it starts a fresh count toward the loop cap.
- When an issue goes back with GitHub comments to carry, the runner clears the flag, unsubscribes the maintainer, and then posts its own comment, such as "🔴 Back to build: your GitHub review, 3 comments". The `Details` fold quotes each comment with its file, line, commit, and permalink. The comment notifies nobody, and build reads it from Linear like any handoff.
- The runner returns the PR to draft, as it does when a bot round sends work back (ADR 0010). Once check passes the fix, the runner marks the PR ready, the bots review the new commit, a bot round runs if they leave findings, and the flag returns.
- Build does what each change request asks, and a change request wins over any criterion it contradicts. Build's pause rules don't apply to what a change request explicitly asks for, such as a new dependency. A change request accepts a break only under plan's test (ADR 0026): it has to say the old form stops working. A bare "rename this" makes build pause under its rule 2 and propose keeping the old name as a deprecated alias. Build pauses only when it can't tell what the maintainer wants or when two change requests conflict. A change request that asks a question gets an answer, not a code change.
- Check judges each change request. One that build didn't handle becomes a finding with a failing case. Check drops a reviewer's finding against something a change request explicitly asked for, and cites the change request. For merge risk, a change that a change request asked for doesn't count against Alignment (ADR 0020).
- Once check passes the commit, the runner replies in each of the maintainer's threads that build acted on and resolves the thread. The reply is "Fixed in <short SHA>." for a change, or build's answer of one or two sentences for a question. A change request that paused the issue gets no reply, and its thread stays open. Review bodies and top-level comments get no reply, so build answers them only in its Linear handoff. If a fix isn't right, the maintainer unresolves the thread, and it carries again. ADR 0020 said the factory never replies to a person on its PR. It now replies to the maintainer in threads they started, and to nobody else.
- A send-back from the maintainer starts a fresh count toward the loop cap of 3 (ADR 0007), because the maintainer chose to spend those rounds. It also counts toward debrief's Sent back signal (ADR 0012), whose threshold stays at 1. When the change requests were a matter of taste, debrief files nothing.
- On a spec, the spec PR and the spec issue take change requests, and build on the spec acts on them, as it does on the spec check's findings (ADR 0004). A comment on a landed sub-issue reaches nobody, because the flag sits on the spec.
