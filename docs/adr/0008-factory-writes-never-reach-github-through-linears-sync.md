# Factory writes never reach GitHub through Linear's sync

Linear's GitHub Issues Sync copies a Linear issue's description to the GitHub issue body. Two-way sync does this by design, and one-way sync does it too: on Shaders, a description the Flight Deck app user wrote replaced the GitHub issue's body within 15 seconds, edited by Linear's `linear-code` GitHub App. No setting keeps a single edit from syncing. Plan replaces an issue's description with its brief, so on a synced issue it would rewrite a stranger's GitHub issue body on a public repo. So before the runner applies plan's brief to a synced issue, it turns off the issue's sync with `issueExternalSyncDisable`. The sync attachment stays on the issue as its link to the GitHub issue. The GitHub issue keeps the reporter's text. The runner posts every factory comment as a top-level comment, outside the issue's synced thread, and Linear keeps those comments out of GitHub. The brief's Context carries the GitHub issue's link, so build's PR closes the GitHub issue with `Fixes owner/repo#N` when it merges.

## Considered options

- **Let the brief reach GitHub.** The GitHub issue would show the brief as an edit by `linear-code`, with the report in a Linear fold that GitHub may not render.
- **Put the brief in a comment on synced issues only.** The brief would live in one of two places, depending on where the issue came from. The maintainer can't edit a comment the Flight Deck app user posted, which breaks the rule that only the maintainer edits the brief after plan writes it.
- **Delete the sync attachment and add a plain link.** `attachmentDelete` stops the sync as well, but the link to the GitHub issue goes with it. Putting the link back takes a second call, `attachmentCreate`, and the new link belongs to the Flight Deck app instead of the GitHub integration.

## Consequences

- A detached issue stays detached. A reporter's later GitHub comments stop reaching Linear, and closing or reopening the GitHub issue no longer moves the Linear issue. The maintainer sees those changes only as GitHub notifications. The runner fetches the GitHub issue's body and comments into each session's inbox (ADR 0013).
- A pause asks the maintainer, never the filer. Until the detach, a factory reply in the synced thread would reach GitHub as a `linear-code[bot]` comment that opens with "from flightdeck:", so the runner never writes in that thread. The maintainer passes any question on to the reporter.
- Until the detach, the factory's status moves keep a synced issue open on GitHub, because Linear maps every unstarted and started status to open. Canceled closes the GitHub issue as not planned, as `linear-code[bot]` when the Flight Deck app user moves it and as the maintainer's connected GitHub account when they do.
- GitHub issues arrive through one-way sync, and setup won't add a factory to a team that syncs two-way (ADR 0013). One-way sync still carries comments and open or closed status in both directions, so the runner detaches every synced issue before it applies a brief.
- The runner also detaches a synced issue before it marks the issue a duplicate, so the move never closes the GitHub issue. The GitHub issue stays open until the fix lands. When plan works the matching issue, it lists the duplicate's GitHub issue in Context, and build's PR closes both with `Fixes owner/repo#N`.
- A dry run on Shaders confirmed the detach through the API. After either `issueExternalSyncDisable` or `attachmentDelete`, no write from the Flight Deck app user reached GitHub: not a new description, a top-level comment, a reply in the former synced thread, a move to Ready to plan, or a move to Canceled. No GitHub comment, close, or reopen reached Linear, including on issues held in Planning.
