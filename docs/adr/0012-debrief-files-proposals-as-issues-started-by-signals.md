# Debrief files proposals as issues, started by signals

On the board, `/flight-debrief` ran every Friday and opened one PR with up to 5 changes to checks, standards, and flow skills, then posted a Linear project update. Later decisions broke each part. That PR would be the only change in the repo that build didn't write and check didn't judge. A flow's skill now belongs to Flight Deck, not to the repo. A team can't post a project update. So debrief writes no code. It files each change it proposes as a proposal: an unsent issue in the repo's team, at most 5 per debrief, which the runner flags. The maintainer sends a proposal through plan, build, and check like any other issue, makes the change by hand when it lies outside the repo, or cancels it. Debrief runs when something went wrong, not on a clock. The runner counts each signal in code, the way it already sees every pause and verdict, and a count that reaches its threshold starts a debrief session.

## Considered options

- **The board's Friday routine and PR.** A clock spends a session in a quiet week and doesn't fire while the Mac sleeps. In a busy week, a mistake waits days for its debrief. The PR would skip check, and ADR 0007 would pause it anyway, because it edits `CLAUDE.md` and the repo record.
- **One debrief issue per run that lists the proposals.** The maintainer would have to turn each proposal they accept into an issue by hand.
- **Hand runs only.** The maintainer would run `/flight-debrief` when something bothered them, and `flight-deck status` would show the counts. A hands-off maintainer rarely notices the pattern a count catches.
- **A notes file for each flow in the repo**, such as `.flight-deck/notes/build.md`, so debrief could correct a flow locally. Each repo would fork Flight Deck's behavior, and the notes would go stale across updates. A repo already steers every flow through `CLAUDE.md`, `CODING_STANDARDS.md`, and its slots.
- **Proposals whose evidence holds skip the send.** On Shaders, the maintainer graded every proposal by its evidence, so a check of the evidence could have stood in for the send. But the send is the only point where a person reads text before the factory acts on it, and debrief reads transcripts that can hold a stranger's comment. A proposal that skipped the send would carry that text to a pushed branch with nobody reading it. Most proposals need the maintainer anyway. Of the 14 on Shaders, 7 were upstream reports and 1 lay outside the repo, and a proposal that edits the record, `CLAUDE.md`, or `AGENTS.md` pauses before check (ADR 0007). Skipping the send would save one decision per proposal, and debriefs are rare.

## Consequences

- Flight Deck ships ten signals with default thresholds. "Review /flight-debrief for a solo maintainer on any repo" lists eight. "Can debrief turn the Shaders dry runs' failures into proposals the maintainer would send?" added two, because the first debriefs on Shaders never saw a check pause or a rough brief. Check pauses, at 1, counts every pause check raises, except one for a diff that edits the record, `CLAUDE.md`, or `AGENTS.md`. Brief gaps, at 2, counts each change build made that the brief didn't ask for and each criterion build couldn't prove the way the brief named it, except a regression guard and a criterion the brief leaves to CI. A change that a change request asked for counts as asked. Sent back, at 1, counts each time the maintainer sends an In Review issue back, whether by a move in Linear, by a Request changes review, or by a review the runner finds when check passes the issue (ADR 0023). It also counts a PR the maintainer closes unmerged. The repo record can override any threshold, and a threshold of 0 turns its signal off. Each count covers the time since the last debrief, so no evidence gets debriefed twice. At most one debrief runs per repo at a time.
- ADR 0011 said follow-up issues flag nothing. A proposal is flagged, because it exists only to get the maintainer's decision.
- A fix to one of Flight Deck's own flows becomes an upstream report. That is a proposal outside the repo, with a link that opens a prefilled issue on Flight Deck's GitHub repo. Nothing leaves the Mac unless the maintainer files it. Debrief writes no eval cases.
- The runner keeps each session's transcript in its data folder for 30 days. A debrief resets every count, so when a signal crosses its threshold, the runner copies into debrief's inbox the transcripts of the issues behind every counted event, not only the events behind that signal. Debrief starts from the events, reads each issue's whole history, and picks the transcripts it needs, which it reads as untrusted text. The runner's secret scan covers every proposal before the runner files it.
- A setup gap qualifies for a proposal the first time debrief sees it, because it recurs on every run it touches. A session's mistake needs two problems, or a written repo rule that nothing enforces. When debrief can't tell which it is, it files the gap and says what's uncertain.
- Debrief proves each check it proposes. It runs the record's dependency install, adds the check in its worktree, runs it against the past mistake and on the default branch, and undoes the change before it exits.
- Before debrief writes its outbox, a reviewer subagent checks every proposal and every comment on an open proposal. It reads them, the inbox, the worktree, and the installed flows, but none of debrief's notes. It rates the evidence for each as holds, partly, or none. It also looks for a fix that can't work, by reading the output of debrief's proof or by running what it can in the sandbox. And it looks for a change already decided in the repo's docs, in the installed flows, or by an open proposal or one canceled in the last 90 days. Debrief revises anything the reviewer doesn't rate holds once, and the reviewer rates it again. Debrief files and comments only what the reviewer rates holds and drops the rest. If a dropped cause is real, its signal crosses again. On Shaders, the evidence for 3 of 14 proposals didn't hold, and the maintainer couldn't tell which from the text.
- Each proposal opens with a block of under 150 words that the maintainer decides from: where the change lands and whether anything gets weaker, what happened, what changes, what it costs, and how sure debrief is. The last line names anything the reviewer couldn't reach, such as a decision outside the repo's team or in a newer version of Flight Deck. The cause, evidence, change, and proof follow it. On Shaders, the maintainer couldn't decide from proposals that opened with transcript lines and rule numbers.
- The maintainer sends a proposal by moving it to Ready to plan and cancels it by moving it to Canceled. After making a change outside the repo by hand, or filing an upstream report, they move it to Done. A proposal offers no one-word answers, because each of those statuses carries one decision (ADR 0019). Its flag's status line reads "🟡 Needs your decision".
- Debrief's default time limit is 20 minutes. Debriefs on Shaders took 2 to 8, and none of them ran the reviewer.
- A proposal loosens something when it removes or relaxes a check, a standard, or a steering rule, or when it widens what sessions can reach. Its title then starts with "Loosens:", and its first sentence says what gets weaker and why.
- The runner keeps a list of the proposals it has filed, so no label marks them. Debrief comments new evidence on an open proposal instead of filing it again. It doesn't refile a change the maintainer canceled in the last 90 days.
- No project update and no daily brief carries debrief's output. `flight-deck status` shows each count and when the last debrief ran.
