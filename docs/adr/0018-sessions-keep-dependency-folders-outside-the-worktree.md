# Sessions keep dependency folders outside the worktree, and only the runner writes the dependency cache

Each factory session runs the repo's dependency install as its first command, inside Claude Code's Bash sandbox (ADR 0007). On macOS that sandbox denies writes to its protected names, such as `.idea`, `.vscode`, `.gitmodules`, and `.mcp.json`, at any depth below the working directory, `node_modules` included. Only `filesystem.disabled` lifts the deny. On Shaders, `javascript-natural-sort` ships an `.idea` folder, so `pnpm install` fails. So before a session starts, the runner replaces each dependency folder the repo record lists, such as `node_modules`, with a symlink to a folder outside the worktree that `--settings` makes writable. The deny stops at the working directory, so the dependency install writes through the symlink. Node resolves a package from its real path and walks up through the `node_modules` folders above it. Moving the whole folder keeps that walk intact, so packages resolve the way they do in CI. Downloads through Claude Code's sandbox proxy are slow, so the runner also keeps one dependency cache per repo. Only the runner writes it, by running the dependency install under a pinned `sandbox-runtime` on the default branch whenever that branch moves. Nothing the repo controls runs or fetches outside a sandbox, even with scripts off. Each session gets a writable copy-on-write APFS clone of the cache, and the runner deletes the clone when the session exits. No session can change the packages a later session runs.

## Considered options

- **The runner installs outside the sandbox with scripts off.** Turning scripts off still leaves the repo's code running. pnpm runs `.pnpmfile.cjs` and `configDependencies`, npm runs the program the repo's `.npmrc` names as `git`, and Bun runs a `bunfig.toml` security scanner. Yarn Berry has no `--ignore-scripts`, and it runs `yarnPath` and plugins on every command. A build session can edit all of these files, and a lockfile can send a fetch to any host. Check's install would follow build's edits with the runner's full access.
- **The dependency install, or the whole session, under `srt`.** `srt` is the same sandbox code Claude Code bundles, and it denies the same folders at the same depth.
- **Moving only part of the tree.** pnpm's `--virtual-store-dir` outside the worktree installed on Shaders, but `@testing-library/jest-dom` could no longer resolve `vitest`, and typecheck failed with 24 errors that CI doesn't see. pnpm's global virtual store keeps `node_modules` in the worktree, but it is experimental and works only for pnpm. It also resolves hoisted packages through `NODE_PATH`, which ESM imports ignore.
- **One package store that every session writes.** The runner prototype did this. A build session that patched a package in the store, because of a planted instruction or to fix a dependency in place, would change what check's tests run against. Check would then pass code that fails in CI.
- **No cache, or a cache that a `claude -p` warm-up session refreshes.** On Shaders, a cold install through the sandbox proxy took 507 s, and every issue runs three stages. A warm-up session would also spend plan usage and download through the same slow proxy. Through `srt`'s proxy, a cold refresh of all of Shaders took 64 to 84 s, about 2.5 times a direct install's 30 s, which is fast enough for a refresh that runs only when the default branch moves. The 507 s ran under launchd's `Background` process type, which ADR 0002 later dropped because it slowed every session about tenfold. Under `Standard`, a cold install inside a session took 39 s, and an install from the cache took 4.5 s, so the cache saves about half a minute a session.

## Consequences

- The repo record lists the repo's dependency folders. Setup proposes the root `node_modules` for a JavaScript repo, adds any folder the trial run's denials name, and the maintainer confirms the list. The record's command category for the dependency install is `dependencies`.
- The runner points each symlink at a folder that already holds a file, because pnpm 11 deletes an empty target and then fails. It adds each folder to `info/exclude` in Flight Deck's clone of the repo. A `.gitignore` entry of `node_modules/` doesn't match a symlink, so `git add -A` would otherwise commit it.
- A refresh runs the dependency install in a scratch worktree of the default branch, with the same symlinks. Its `sandbox-runtime` settings come from the same source as a session's sandbox settings: the record's hosts and the same kinds of writable paths. A failed refresh keeps the last good cache. A spec branch's new dependencies download in each session until the spec merges. A repo with no cache gets a refresh before its next session, whether or not the default branch moved. After `flight-deck remove` and a second setup, Shaders had no cache until a refresh ran by hand.
- pnpm writes the links in `node_modules` relative to the worktree it ran in, so the cached `node_modules` never works in another worktree as it stands. Each session's dependency install purges it and relinks from the cloned package store, in 4.5 s on Shaders. The store is the part of the cache that saves time. The cache stayed byte-identical after every session, including one that wrote 1.8 GB into its clone.
- The symlink targets resolve to a path outside the worktree. Vite's dev server serves only files under its `server.fs.allow` list, which holds the worktree, so it answers 403 for a package's real path. Shaders runs Next, and Vitest in Node, so nothing there asks for the real path. A Vite app or Vitest in browser mode would, and the trial run shows it.
- The dependency install follows the repo's own build-script approvals. Flight Deck never adds one.
- In v1, dependency installs use only registries that need no credential, and sessions read Flight Deck's own npm config instead of `~/.npmrc` (ADR 0007). A read token in a session could leave through any host on the record's list. If the trial run's dependency install fails on authentication, setup names the failure and stops.
- Sessions run the package manager installed on the Mac. Setup finds it on the maintainer's `PATH` and keeps its absolute path in the Mac's registration of the repo, not in the record. Some package managers switch to the version the repo pins, such as pnpm through the `packageManager` field and Yarn through `yarnPath`. There the pin wins, and the record lists the hosts that download needs, such as `nodejs.org`.
- In plan and build, a dependency install that fails on the base gets the stage's one retry, and then the issue pauses. If the default branch itself fails, plan also files a follow-up issue. In check, a failure on build's commit is a finding. A sandbox denial pauses the issue and names the host or path the record lacks, including a new host for a dependency build added.
- Two open `sandbox-runtime` pull requests could change this. #541 exempts `node_modules` on macOS, which would make the symlinks unnecessary. #518 applies the denies to every `allowWrite` root, which would break them. Claude Code updates itself, so nothing catches #518 ahead of time. A session's dependency install would fail with a write error under a symlinked folder, and the runner would pause the issue. The refresh runs the `sandbox-runtime` version Flight Deck pins, so it changes only with a Flight Deck update.
