# The runner flags the maintainer by assigning them

A hands-off maintainer needs to hear about the issues that need them, and only those. On the board, `/flight-log` was a session that wrote a daily brief and posted it as a comment. The runner applies every outbox, so it learns about each pause and each passed check as it happens, and it makes no model calls. So `/flight-log` is no longer a flow, and no brief replaces it. When an issue needs the maintainer, the runner flags it by assigning it to them. It assigns first and posts the comment that says why second, so that comment reaches the maintainer's phone (ADR 0019). A flag covers a pause, a change ready for review once its bot round settles, and a stale take. It also covers a proposal that debrief files (ADR 0012) and an issue the runner files about a review bot that stopped reviewing (ADR 0016) or about trouble with the runner itself. Whenever the runner finds the maintainer subscribed to an unflagged issue in a factory status, it unsubscribes them, so the factory's handoff comments stay out of the maintainer's Linear inbox. Everything else the maintainer looks up when they choose: My Issues, the views that setup creates, `flight-deck status`, and the menu bar app (ADR 0021).

## Considered options

- **The board's daily brief.** A session would spend plan limits every weekday writing prose about a list of issue links. Each item on it either needs the maintainer now, and the next morning's brief is too late, or doesn't need them at all. A daily post that repeats unread notifications teaches the maintainer to skip it.
- **A view subscription on a "Needs you" view.** Setup could subscribe the maintainer under their own login. A view filters only on Linear fields, so its notification would fire when an issue enters In Review, before its bot round settles. ADR 0010 rules that out. Setup still creates a Needs you view to look at, filtered on the flag itself (ADR 0021).
- **Leave subscriptions alone, and let the maintainer filter.** Linear puts every notification in the inbox, and no preference keeps one out. Preferences control only desktop, mobile, email, and Slack, so turning off comment push would also mute comments from people.

## Consequences

- ADR 0006 said the factory never sets an issue's assignee. While an issue sits in a factory status, the factory now owns its assignee. The runner clears an assignee set before the maintainer sent the issue, assigns the maintainer to flag it, and clears the assignee when the issue goes back into a factory queue. Outside the factory's statuses, the assignee is the maintainer's, so a merged issue keeps its assignee. The factory still never sets a delegate.
- Linear always subscribes an assignee, so a flagged issue's comments reach the maintainer until the flag clears. Clearing the assignee archives the "assigned to you" notification. If the maintainer hasn't read it, nothing else arrives. If they have, Linear also sends "Flight Deck unassigned you", in the Assignments category. Answering a pause means opening the issue, which marks the flag read, so an answered flag ends with that one extra notification.
- The maintainer is subscribed to every issue they file, and Linear subscribes them again after each flag and each comment they post. So the runner unsubscribes them with `issueUnsubscribe(id, userId)` whenever it finds them subscribed to an unflagged issue in a factory status, not only at a take. A sent issue that waits on a blocker then sends no "no longer blocked" notification. An unsent issue still does, because it stays the maintainer's. To clear a flag, the runner clears the assignee before it unsubscribes the maintainer, because Linear keeps an assignee subscribed. On an unflagged issue, it unsubscribes them before it posts a comment, so the comment notifies nobody.
- Every unsubscribe that removes the maintainer sends them "Flight Deck unsubscribed you from an issue", and Linear has no silent way to remove a subscriber. Removing them through `subscriberIds` in `issueUpdate` sends the same notification. Unsubscribing a user who isn't subscribed sends nothing. The notification, of type `issueUnsubscribed`, sits in Linear's Subscriptions category, apart from assignments and comments, so setup proposes turning off that category's mobile, desktop, and email notifications (ADR 0017). The maintainer's Linear inbox still gets one for each issue the maintainer files and one each time a flagged issue goes back into a factory queue.
- `flight-deck stop` flags nothing, because the maintainer stopped the factory. Follow-up issues, plan-limit holds, and landings flag nothing either. ADR 0012 flags each proposal that debrief files, because a proposal exists only to get the maintainer's decision.
- Setup creates two shared views in each factory's team under the maintainer's login, beside the workspace's Needs you view (ADR 0021). "In flight" lists every issue in a factory status, grouped by status, including those `flight-deck stop` paused without a flag. "Filed by Flight Deck" lists the unsent issues the Flight Deck app user created in Backlog, Triage, or Todo, such as follow-up issues, proposals, and trouble issues.
- A stale take is an issue that has sat in a working status longer than its stage's time limit with no take the runner recorded, such as a flow run by hand that never finished. The runner flags it once, with a comment that names the status and how long the issue has sat there, and otherwise leaves the issue alone. The time limit keeps a hand run still in progress from being flagged.
- Some trouble stops more than one issue. An expired Claude login, an expired token for the machine user, or a Linear token the runner can't mint (ADR 0005) stops the whole runner, and a factory status missing from a team stops that repo's factory (ADR 0006). Issues then wait in their queues, none of them pauses, and no issue is left to flag. The runner files one issue per cause in each affected factory's `intake` status (ADR 0013), flags it, and posts a macOS notification with `osascript` in case the Linear credential is what broke. While a cause's issue is open, the runner doesn't file that cause again. When the cause clears, the runner comments on the issue. The maintainer closes that issue, so the runner still closes issues in only the three cases the lifecycle allows.
- Silence can't tell a quiet day from a dead runner. launchd restarts a runner that crashes, and a closed lid stops the factory (ADR 0002). The menu bar app says when the runner stops responding (ADR 0021).
