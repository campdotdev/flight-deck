# The menu bar app ships in each version and runs the runner's version

ADR 0021 chose a menu bar app, but the runner is one Bun binary (ADR 0015), and Bun has no menu bar API. So the app is a small Swift app on SwiftUI's `MenuBarExtra`, built with `swiftc` and signed ad hoc like the runner. Each version's tarball carries it as `Flight Deck.app` beside the runner, so `install.sh`, `flight-deck update`, rollback, and pruning treat it like every other file in the version. `flight-deck install` loads it as a second LaunchAgent, which starts it at login. The runner restarts that agent each time the runner itself starts, so once an update drains, the app runs the same version as the runner. A prototype on the maintainer's Mac shipped four builds this way through `install.sh`, with no Gatekeeper or privacy prompt.

## Considered options

- **The runner binary, reaching AppKit through `bun:ffi`.** One binary would do both jobs. The app would have to run AppKit's main run loop inside Bun's event loop and create an Objective-C class by hand for each menu action. The prototype didn't build it.
- **A Developer ID signature.** It costs $99 a year for the Apple Developer Program, plus a certificate and notarization in release CI. Login Items would then show both agents under the app's name and icon, because Background Task Management honors `AssociatedBundleIdentifiers` only with a Team ID. Launchers that never change already stop the repeated notices, and nothing else in v1 needs a Team ID.
- **A login item through `SMAppService.mainApp`.** It registers the bundle that calls it. That bundle sits in one version folder, which a later update prunes.
- **The runner opens the app itself.** One LaunchAgent would do instead of two, but a crashed app would stay gone until the runner's next start.

## Consequences

- Release CI builds the app with `swiftc` on a macOS arm64 runner with a pinned Xcode. It needs no Xcode project, no SwiftPM, and no Apple Developer account, and the bundle is 164 KB. A Mac's Command Line Tools can default to an SDK their own compiler can't read: this Mac's defaulted to a macOS 27 SDK that its Swift 6.3.3 rejects. So a local build names its SDK.
- The app needs macOS 13, the floor that Claude Code and Bun already set.
- `curl` and `tar` set no quarantine flag, so Gatekeeper never blocks the app. `syspolicyd` still scans each new build once at its first launch, runs XProtect on it for about 0.6 s, and allows it. The release tars with no extended attributes, because `tar` restores any attribute the tarball carries, a quarantine flag included.
- Background Task Management records each LaunchAgent's executable and posts "“<name>” can run in the background" when an agent is new or its executable changes. An ad-hoc build behind `current` gets a new identity every time, so every update would post the notice again at the next rescan. Writing any plist in `~/Library/LaunchAgents` starts one. For the prototype runner's agent, macOS logged "Exceeded max notifications for flight-deck. Please file a Feedback report or contact the developer."
- So both agents point at launchers that never change, in `~/.local/share/flight-deck/launch/`. Each launcher `exec`s its binary through `current`. Install writes them once: `flight-deck` for the runner and `Flight Deck` for the app. The notice and Login Items show each launcher's name. In the prototype, a rescan after an update flagged the runner's agent, which still pointed through `current`, and left the app's agent alone. This replaces the runner agent's direct path to `current/bin/flight-deck` from ADR 0002 and ADR 0015.
- Login Items lists the two agents separately, because Background Task Management ignores `AssociatedBundleIdentifiers` without a Team ID.
- The app's agent sets `RunAtLoad`, `KeepAlive` only on a crash, `LimitLoadToSessionType` to `Aqua`, and `ProcessType` to `Interactive`. A crash brings the app back. After a force quit, it stays gone until the next login or the runner's next start.
- The menu has no **Quit** item, because ADR 0021's menu has none. macOS 26 can hide any menu bar item from **System Settings → Menu Bar**, and Login Items turns the agent off.
- `flight-deck update` does nothing to the app itself. While the runner drains, the app stays on the old version with the runner it watches. The runner's `launchctl kickstart -k` at its start then moves the app to the new version, and a rollback works the same way. The app resolves `current` to its own version folder, so its controls run that folder's `flight-deck`, never a newer one than the runner.
- Pruning a version folder deletes its app too. The launchd-started prototype runner deleted one that had run, with no App Management prompt.
- `flight-deck uninstall` (ADR 0017) unloads both agents and deletes both launchers and the app's saved place.
- macOS puts a new menu bar item at the left end of the row. On a full menu bar, as on a notched MacBook, it doesn't draw the item at all, and the maintainer's Mac hid the app this way. So at its first launch, the app asks once for a place 330 points from the right edge, through its `NSStatusItem Preferred Position Item-0` default. Another app's icon may drop off the left end instead. A Cmd-drag moves the app after that, and macOS keeps the new place.
- Every 5 seconds, the app reads the state the runner rewrites at each poll, and the hold marker that `flight-deck hold` and `flight-deck stop` write. Reading the marker shows a hold at once, not a poll later. The marker names the command that wrote it, so the icon can tell a hold from a stop.
- The app holds no credential and needs no privacy grant. It reads files under `~/.local/share/flight-deck/`, runs `flight-deck`, and opens Linear. So its identity can change with every build, and an update loses nothing.
