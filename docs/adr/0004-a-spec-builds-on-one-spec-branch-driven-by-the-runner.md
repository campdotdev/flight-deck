# A spec builds on one spec branch, and the runner drives its issues

When the maintainer sends a spec, the runner cuts one spec branch from the default branch and starts each sub-issue once its blockers have landed there. Each sub-issue still passes through plan, build, and check in sessions of its own, under the concurrency cap. An issue lands when the runner fast-forwards the spec branch to the exact commit check passed, so every commit on the spec branch is one that check judged. Sub-issues open no PRs. When the last one lands, build takes the spec issue itself, and the spec branch becomes one PR. A spec check judges the whole change, and the maintainer merges once. An issue outside a spec keeps its own branch off the default branch and its own PR.

## Considered options

- **The board's model: one PR per issue, off the default branch.** A blocked issue would wait for its blockers to merge, so the maintainer's merges would set the pace. A chain of six issues would need six rounds of build and check with a merge between each, and the spec would reach the default branch one slice at a time.
- **`implement-spec` as one factory session.** One `claude -p` run would build the spec with parallel subagents on an integration branch. That puts taking issues, worktrees, the cap, and recovery back into prompt text, which ADR 0002 moved into the runner. The subagents would run outside the cap, a crash would restart the whole spec, and check would judge one large diff.
- **Stacked PRs.** Each issue's PR would target its blocker's branch. A fix low in the stack rebases every branch above it, and under ADR 0001 every new commit sends an issue back through check. The maintainer would still merge one PR per issue.
- **Landing with a merge commit when the merge is clean.** This saves a second check when two siblings run side by side. Two siblings that each pass but break each other would then show up only on the spec PR.

## Consequences

- A blocker counts as landed when its status is Landed or Done. The runner tests each blocker's status, not its status type, because Landed is a `started` status. Plan and build on a sub-issue start from the spec branch's tip, so the brief describes the code build starts from.
- The runner lands a sub-issue as soon as check's session passes it, and moves it from In Review to Landed. When a sibling has landed first, the runner merges the new tip into the waiting issue's branch if git reports no conflict, and moves the issue back to Ready to check, so check judges it again. A conflict moves the issue to Ready to build. The runner's merge commit adds no lines of its own, so build is still the only stage that writes code.
- A PR into a spec branch would skip much of a repo's CI. On Shaders, `ci.yml` runs only for PRs into `main`. CodeRabbit, and Copilot when a ruleset requests it, review only the default branch unless configured otherwise. A sub-issue's check runs the repo record's local commands instead. Full CI and every review bot run only on the spec PR.
- Landed issues stay open until the spec PR merges, so Done still means the work is on the default branch. Linear's merge automation then moves the spec to Done, and the runner moves every landed sub-issue to Done.
- The spec issue skips plan, because its body is the spec. When the runner cuts the spec branch, it moves the spec to Ready to build, where the spec waits until every open sub-issue has landed. A sub-issue writes no changeset, and its claims say "no changeset: build on the spec writes it". Build on the spec writes the spec's changesets, grouped by concept, never by sub-issue. In the same way, a sub-issue's build never pauses for a rendered file under a `pause` entry. Its claims say "rendered file: build on the spec asks for it", and build on the spec pauses once for every such file (ADR 0022).
- The spec check sends its findings to build, which works on the spec issue itself. The runner pushes build's commits to the spec branch (ADR 0007). The spec PR goes through ADR 0001's loop like any other PR.
- The spec check reads full CI and reruns the local commands. It re-proves every sub-issue criterion whose proof is the running app or a CI-only command, and every criterion a sub-issue left unproven, because a sibling's re-check re-proves only its own criteria. A user story counts as proven when a criterion that covers it was proven or re-proven in this verdict. The spec check proves in the running app only the user stories no criterion covers, and a spec with no User Stories section relies on its sub-issues' criteria. It reviews the whole spec diff only for problems that cross issues: duplication between siblings, names or seams that disagree, and leftovers. Its ledger on the spec issue maps each user story to its proof and lists every sub-issue criterion with its latest proof, unproven first.
- A spec with a sub-issue blocked from outside the spec doesn't start until that blocker is Done. `/flight-new` files standalone work, such as a rename or a break of a public contract, as an independent issue with no blocking relation to the spec. The spec builds on whatever the default branch holds when it is sent, and the standalone issue adapts to whatever lands first. The spec branch takes the default branch's new commits only through build on the spec, which merges the default branch's latest tip every time it runs (ADR 0027). Build on the spec also runs when the open spec PR conflicts with the default branch or its CI fails because the default branch moved.
- The runner takes a sub-issue from Ready to plan only while its spec is sent. Moving the spec back to Backlog keeps the runner from taking any sub-issue that hasn't started a session. A sub-issue that is paused or moved back to Backlog stops only the sub-issues it blocks, and the spec PR waits for it. A sub-issue added while the spec builds joins it. If the spec PR is already open, the new landing moves its head, and the spec check runs again.
- A canceled blocker never lands, so the runner pauses an issue whose blocker was canceled and asks the maintainer to remove the blocking relation or restore the blocker. When the maintainer cancels a spec, the runner cancels its open sub-issues, starts nothing more for it, and leaves the spec branch for the maintainer to keep or delete.
