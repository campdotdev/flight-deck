# Setup proposes in a session and writes through the CLI after one confirmed plan

Setup does two kinds of work. Reading a repo and proposing its record takes judgment, so the `/flight-setup` skill does that in the maintainer's own Claude Code session. Every change outside the maintainer's checkout is mechanical: statuses, views, team settings, the ruleset, and the machine user's invite, which setup accepts with the machine user's own token. Those writes go through `flight-deck setup` subcommands, which hold a personal Linear key the maintainer creates for setup, limited to Read, Write, and Admin, with no team limit, because each new factory adds a team. No secret passes through a session (ADR 0015).

`flight-deck setup check` only reads, so setup can refuse a repo before it writes anything. The skill then writes a draft record into the checkout. `flight-deck setup trial` runs one trial run, `flight-deck setup plan` shows one plan of every write, and `flight-deck setup apply` makes those writes. Nothing outside the checkout changes until the maintainer confirms that plan. There are two exceptions: creating a workspace's two Linear apps, and adding an extra MCP server's entry to the maintainer's Claude Code config so the maintainer can sign in to it before the plan. Setup registers the repo on this Mac last. Each subcommand reads the current state before it writes and writes only what's missing, so a failed setup reruns from the top, the way install does. A failed step stops setup with its error. The rerun skips every step already done, keeps the maintainer's answers in the draft record, and repairs drift, such as a deleted view. On a repo that already has a record, setup writes the migrated record (ADR 0015), offers any new Flight Deck defaults, and shows every change as one diff.

## Considered options

- **The skill makes every write itself.** The GitHub writes could use the maintainer's `gh` login, but the Linear writes need the personal key, which can't enter a session. With the writes split between the skill and the CLI, a rerun would have to guess where the last run stopped.
- **A terminal wizard with no Claude session.** Every step would be deterministic. Nothing would read the repo's scripts, workflows, and instructions with judgment, and that reading is most of setup's work.

## Consequences

- `flight-deck setup check` refuses the repo unless install is done, the runner is up, the repo has a GitHub remote and a default branch, and the maintainer's `gh` login is an admin on it. The personal key can't list OAuth apps, so `check` mints a client-credentials token from each app to learn whether the workspace has Flight Deck, with `read` and `write`, and Flight Deck Reader, with `read` (ADR 0005). For each app it lacks, setup opens a manifest link that pre-fills Linear's new-app form, and the maintainer clicks Create. Only a workspace admin can create an app. The form's callback URL can be any localhost URL, because the client-credentials grant never calls it. The maintainer then runs `flight-deck login linear <workspace>`, which stores both apps' secrets and the personal key, `LINEAR_SETUP_KEY`, in `credentials.env`. `check` revokes each token it minted.
- Setup leaves the record as one uncommitted diff, and the maintainer commits it the way the repo commits anything. An issue sent before the record reaches the default branch pauses with that reason, and `flight-deck status` shows the repo as waiting for its record.
- The trial run is a sandboxed session that runs the dependency install, every local command, and the app the way the runner will, in a fresh worktree of the runner's clone with the draft record copied in. Claude Code logs no sandbox violations, so setup reads each failure from the command's own output. If the output names a denied host, or a path under `~` that the record may reopen (ADR 0007), setup proposes adding it and reruns the command. If the maintainer declines, the command is CI-only. If the dependency install fails even with those fixes, setup stops. If a command fails and its output names no denied host or path, setup runs it once more outside the sandbox, in the maintainer's session. That tells a sandbox failure from a failure on the default branch. ADR 0007's limits don't cover setup, which the maintainer runs in their own agent. A command that fails outside the sandbox too stays in the record, and setup offers a gap issue for it.
- A sandbox failure that no host or path in the record fixes is Flight Deck's problem. Setup reports it and keeps the repo's own command. Before the runner fixed four such failures on Shaders, setup's draft moved the build to CI, built only the packages locally, and capped the app's open files. A session on that record would have checked less than CI does.
- Setup runs ADR 0025's CI audit under the maintainer's login, because only an admin can read the repo's Actions settings and its self-hosted runner list. When a job fails, setup's uncommitted diff adds the guard that skips the job on the machine user's PRs, so the maintainer reviews and commits it with the record. A settings change, such as turning off "Allow GitHub Actions to create and approve pull requests", goes into the one plan as a `flight-deck setup` write. That write sets `can_approve_pull_request_reviews` to `false` with `PUT /repos/{owner}/{repo}/actions/permissions/workflow`. A fix that needs a new credential is a step the maintainer does by hand before confirming the plan, and setup names it. On Shaders, Changesets needs its own token before create-and-approve can go off, so setup leaves the setting on until the maintainer has added one. Until the audit passes, the runner pushes nothing for the repo.
- The plan lists the record diff, every Linear and GitHub write, the gap issues on offer, and the hand steps, which setup checks once the maintainer has done them. Setup turns off Linear's linkback comments for public repos, because a linkback posts the issue's title and description, with the report in its fold, on the PR. Workspace-wide changes, such as the linkback settings, appear apart in the plan, because they change every team in the workspace.
- Setup's Linear writes use GraphQL: `workflowStateCreate` and `workflowStateUpdate` for the statuses and the mark, `teamUpdate` with `triageEnabled`, `gitAutomationStateDelete` for the PR automations (ADR 0006), `customViewCreate` and `customViewUpdate`, `issueCreate` for gap issues, `userSettingsUpdate` for the `subscriptions` category, and `organizationUpdate` for the linkback settings. `flight-deck remove` adds `workflowStateArchive` and `customViewDelete`. Setup also grants both apps access to a private team, because a client-credentials token reaches only public teams.
- Setup writes a factory mark into the description of the team's Ready to plan status. The mark names the repo and the Mac that runs its factory, such as "Flight Deck factory for campdotdev/shaders, run on Hunter's MacBook Pro". If the mark names another repo, setup refuses the team. If it names another Mac, setup names that Mac in its warning and applies nothing until that Mac unregisters the repo or the maintainer confirms the move. `flight-deck remove` refuses that team. Without that refusal, `remove` would clear the other Mac's name and archive the statuses its runner works in. If the mark names this repo and no Mac, the factory has moved, and setup adopts its statuses. If statuses with the factory's names carry no mark, setup asks to adopt them and then writes the mark. Setup also adopts a default-branch ruleset that already requires one approval, so it never adds a second one.
- `flight-deck remove` refuses while a session runs on the repo. It removes what only the factory uses: the repo's place on the Mac, its statuses, its two views (ADR 0011), and the machine user's access. It clears the place on the Mac the way `flight-deck unregister` does. It also takes the team's statuses out of the workspace's Needs you view, and deletes that view with the workspace's last factory (ADR 0021). It leaves what guards the repo or reaches past it, such as the record file, the approval ruleset, Triage, the sync, the workspace's settings, open factory PRs and branches, and every issue the factory filed, and it lists each one with a link. Linear can't delete a status, and it archives a status only when every issue in it is archived, so removal moves the issues in the factory statuses to Backlog first. An in-flight issue in In Review stays there with its flag, because its PR passed check and stays open. Remove lists it beside its PR and says that nothing will judge a bot's findings or carry a Request changes review on it again. Merging the PR still moves the issue to Done.
- `flight-deck unregister owner/repo` takes a repo off one Mac and leaves its factory in place. It refuses while a session runs on the repo. It deletes Flight Deck's clone of the repo, its worktrees, and its dependency cache, and it clears this Mac's name from the factory mark. It asks before it deletes the repo's transcripts and signal counts, because debrief on another Mac starts from zero either way. `flight-deck uninstall` unregisters every repo first, so no factory mark names a Mac that no longer runs it (ADR 0015).
- Setup's plan proposes turning off mobile, desktop, and email notifications for the maintainer's Subscriptions category in Linear, because every unsubscribe the runner makes sends one (ADR 0011). The category covers "issues, projects, initiatives, teams, and views you're subscribed to", so muting it also silences a team or view subscription. The plan says so, and it says that Slack notifications for the category stay on. Assignments, status changes, comments, mentions, and Triage have their own categories, so the runner's flags still reach the phone. The maintainer can decline it, and `flight-deck remove` leaves it, because it's the maintainer's own setting.
- A repo's extra MCP server, such as Figma's, runs on the maintainer's sign-in. Claude Code keeps one sign-in per server name and URL, so a sign-in to a plugin's server, such as `plugin:figma:figma`, doesn't reach a session's `figma`. On Shaders, one sign-in to a `figma` server that only one folder could see served every later runner session.
- The sign-in happens before the plan, because the trial's calls to the server decide what the plan proposes. A `whoami` rerun after `apply` would change the design slots after the maintainer confirmed the plan, and `apply` itself runs before any sign-in. When the trial reports that a server in the draft record needs a sign-in, the skill asks the maintainer, then runs `claude mcp add` at local scope for the checkout, with the record's name and URL. The maintainer signs in once with `/mcp`, and setup reruns only that server's trial calls, in one short session started the runner's way. A redo, or a second repo on a Mac that already holds the sign-in, skips both steps. `flight-deck remove` leaves the entry, because it's the maintainer's own config. Claude Code may not show an entry added during a session in that session's `/mcp`, so the skill may send the maintainer to a second terminal to sign in.
- If the maintainer skips the sign-in, or the rerun still fails, setup drops the server from the draft record and leaves empty every slot that needs it. The plan says why. Setup never proposes `design-check` on a seat it hasn't read. Running setup again after a sign-in proposes the slots.
- Setup proposes `design-check` for plan's `design` slot and check's `review` slot only when the maintainer holds a Full or Dev seat, on Professional or higher, in the Figma team that owns each design file. Any other seat or plan gets 20 Figma MCP calls a month, so setup then leaves both slots empty and says why. `whoami` shows the maintainer's seats and plans but not which plan owns a file, so setup asks the maintainer. The record's tool list for Figma is `whoami`, `get_metadata`, `get_screenshot`, `get_design_context`, and `get_variable_defs`, plus `get_code_connect_map` when the repo uses Code Connect. It leaves out `create_session`, though the server's instructions ask for it, because `get_metadata` works without it.
- When the draft record lists Figma's server, the trial run calls `whoami` and then calls `get_screenshot` once on a page the record names and downloads the image. `whoami` confirms that a session started the runner's way reuses the maintainer's sign-in and shows the seat. Setup then decides the design slots from that seat and from the plan the maintainer says owns each file. Setup sets the record's `image_host` to the host the screenshot URL points at only when it puts `design-check` in a slot. On a seat that doesn't qualify, the two calls spend 2 of the month's 20. A trial that called only `whoami` left the host empty on Shaders. A plan session then couldn't download a frame image, and the sandbox denied `www.figma.com`.
- Setup sets the record's CI time limit to twice the longest passing run among the last 30 CI runs on the default branch, rounded up to 5 minutes. A repo with no CI gets no CI limit. If the trial's dependency install and local commands take more than a quarter of build's or check's limit, setup proposes raising that limit by the measured time.
- Setup writes the debrief thresholds into the record the way it writes slot defaults, because a threshold says how strict the factory is with itself on this repo. Bot done rules still ship with each version (ADR 0016), because a rule describes a vendor.
- When setup proposes the `changeset` skill, it also proposes the repo's convention for bumps and for how a break's text tells users to update, from the repo's docs and recent changesets. The maintainer confirms it once. With no break in the history, setup writes out Flight Deck's default. From 1.0 on, a break is `major` and an addition is `minor`. Below 1.0, both are `minor`. Setup also records in `ci_requires_changeset` whether the repo's CI requires a changeset on every PR.
- When the repo publishes a package, setup records the repo's own test that the built package installs and imports as an extra, so check runs it on each PR. With no such test, setup offers a gap issue for one. A repo that publishes or deploys gets a "No rollback procedure" gap issue if it has none, because Flight Deck ships no rollback steps. One that releases by hand gets a gap issue for release automation.
- Setup writes no verification skill, such as pstack's `create-verification-skill`, because the record already says how to start the app and how to tell that it's ready.
