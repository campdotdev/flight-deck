# Setup proposes in a session and writes through the CLI after one confirmed plan

Setup does two kinds of work. Reading a repo and proposing its record takes judgment, so the `/flight-setup` skill does that in the maintainer's own Claude Code session. Every change outside the maintainer's checkout is mechanical: statuses, views, team settings, the ruleset, and the machine user's invite. Those writes go through `flight-deck setup` subcommands, which hold a personal Linear key the maintainer creates for setup, limited to Read, Write, and Admin. No secret passes through a session (ADR 0015). Setup reads first, runs one trial run, and shows one plan of every write. Nothing outside the checkout changes until the maintainer confirms that plan. The one exception is creating a workspace's Flight Deck app. Each subcommand reads the current state before it writes and writes only what's missing, so a failed setup reruns from the top, the way install does.

## Considered options

- **The skill makes every write itself.** The GitHub writes could use the maintainer's `gh` login, but the Linear writes need the personal key, which can't enter a session. With the writes split between the skill and the CLI, a rerun would have to guess where the last run stopped.
- **A terminal wizard with no Claude session.** Every step would be deterministic. Nothing would read the repo's scripts, workflows, and instructions with judgment, and that reading is most of setup's work.

## Consequences

- Setup leaves the record as one uncommitted diff, and the maintainer commits it the way the repo commits anything. An issue sent before the record reaches the default branch pauses.
- The trial run is a sandboxed session that runs the dependency install, every local command, and the app the way the runner will. Claude Code logs no sandbox violations, so setup reads each failure from the command's own output. If a command fails and its output names no denied host or path, setup runs it once more outside the sandbox, in the maintainer's session. That tells a sandbox failure from a failure on the default branch. ADR 0007's limits don't cover a hand-run flow.
- A sandbox failure that no host or path in the record fixes is Flight Deck's problem. Setup reports it and keeps the repo's own command. Before the runner fixed four such failures on Shaders, setup's draft moved the build to CI, built only the packages locally, and capped the app's open files. A session on that record would have checked less than CI does.
- Setup writes a factory mark into the description of the team's Ready to plan status. The mark names the repo and the Mac that runs its factory. If the mark names another repo, setup refuses the team. If it names another Mac, setup names that Mac in its warning, and `flight-deck remove` refuses the team. Without that refusal, `remove` would clear the other Mac's name and archive the statuses its runner works in.
- `flight-deck remove` removes what only the factory uses: the repo's place on the Mac, its statuses, its two views, and the machine user's access. It leaves what guards the repo or reaches past it, such as the approval ruleset, Triage, the sync, and the workspace's settings, and it lists each one. Linear can't delete a status, and it archives a status only when every issue in it is archived, so removal moves the factory's issues to Backlog first.
- `flight-deck unregister` takes a repo off one Mac and leaves its factory in place. `flight-deck uninstall` unregisters every repo first, so no factory mark names a Mac that no longer runs it.
- Setup's plan proposes turning off mobile, desktop, and email notifications for the maintainer's Subscriptions category in Linear, because every unsubscribe the runner makes sends one (ADR 0011). The category covers "issues, projects, initiatives, teams, and views you're subscribed to", so muting it also silences a team or view subscription. The plan says so. Assignments, status changes, comments, mentions, and Triage have their own categories, so the runner's flags still reach the phone. The maintainer can decline it, and `flight-deck remove` leaves it, because it's the maintainer's own setting.
- A repo's extra MCP server, such as Figma's, runs on the maintainer's sign-in. Claude Code keeps one sign-in per server name and URL, so a sign-in to a plugin's server, such as `plugin:figma:figma`, doesn't reach a session's `figma`. Setup's plan adds a server with the record's name and URL to the maintainer's Claude Code config, and the maintainer signs in to it once with `/mcp`. In FLD-42, one sign-in to a `figma` server that only one folder could see served every later runner session.
- When the record puts `design-check` in a slot, the trial run calls `get_screenshot` once and downloads the image, so the record's image host names the host the URL points at. A trial that called only `whoami` left the host empty on Shaders. A plan session then couldn't download a frame image, and the sandbox denied `www.figma.com`.
- Setup writes the debrief thresholds into the record the way it writes slot defaults, because a threshold says how strict the factory is with itself on this repo. Bot done rules still ship with each version (ADR 0016), because a rule describes a vendor.
