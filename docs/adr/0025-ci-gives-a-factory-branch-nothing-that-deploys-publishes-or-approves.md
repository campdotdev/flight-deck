# CI gives a factory branch nothing that deploys, publishes, or approves

The runner pushes each factory branch to the repo itself, so the repo's CI runs the branch's tests and package scripts before check or the maintainer reads them. GitHub holds back secrets and write access only from a fork's PR, and no setting holds back runs from a collaborator's branch. ADR 0007's limits stop at the Mac, so a planted instruction that reaches build's code would reach whatever CI hands that code. So Flight Deck holds a repo's CI to one rule. A job that a factory branch can start gets no secret besides `GITHUB_TOKEN`, no `id-token: write`, and no runner except a GitHub-hosted one. Its token can't write `contents`, `packages`, `deployments`, or `actions`, and it can't approve a PR. Jobs that post only text, such as comments, commit statuses, and check runs, stay allowed. Text can't change what merges, and the maintainer approves the diff, not CI's comments. One piece of runner code, the CI audit, tests a repo against the rule. Setup runs it before it adds a factory, and the runner runs it again before every push.

The rule also covers host builds. Vercel, Netlify, and Cloudflare build pushed branches outside GitHub Actions. The build gets the host's preview variables, and on Vercel it also gets an OIDC token, so a host build hands unread code the reach the rule takes from a job. Apps that only read the code, such as SonarQube Cloud, Codacy, and review bots, stay outside the rule, because they never run it. Flight Deck can't prove that a host build holds nothing without a host token, and Vercel has no read-only token. So a factory branch never gets a host build.

## Considered options

- **Factory PRs from the machine user's fork.** GitHub would hold back secrets and cut the token to read-only on every repo, with no audit. Spec branches would move to the fork, and first-time-contributor approval could hold the first PRs' runs. A private repo runs no workflows for a fork's PR unless the maintainer turns that on. Every job that needs a secret would fail on factory PRs. No doc says Copilot code review or `gh --attach` works on a fork PR, and the change would rewrite ADRs 0004, 0005, 0010, and 0022.
- **Whatever a fork's PR gets,** a read-only token as well as no secrets. It is the easiest rule to test. Every repo whose CI comments on PRs, Shaders among them through React Doctor, would rework its workflows to take away writes that can't merge anything.
- **Setup reports what PR jobs hold, and the maintainer accepts it.** A repo whose PR jobs pass a deploy token to its tests would then be safe only if the maintainer read one report closely.
- **The runner pushes only after check passes.** Check starts once CI finishes and reads its results, and build needs CI's renders (ADR 0022). Check is also a model reading a diff, not a guarantee.
- **Host builds that hold nothing.** The maintainer would clear the secrets out of the host's preview environment and turn off its OIDC token. Flight Deck can't read either setting without a host token, so this is the report the maintainer accepts, which the rule already turns down for jobs.
- **A CI audit that reads each host's API.** Setup would need a token for each host, and every Vercel token can write. The runner would carry code for three or more hosts, and a branch can still override most host settings from a file it edits.
- **Hosts outside the rule.** "Nothing that deploys" would be false for every repo on Vercel or Cloudflare Pages, which build every pushed branch by default.

## Consequences

- The CI audit counts every workflow on the default branch and every workflow a ruleset requires. It skips a workflow only when the factory can't cause any of its triggers: `schedule`, `workflow_dispatch`, `repository_dispatch`, `release`, `merge_group`, and `push` limited to the default branch or to tags. The runner's replies in bot threads start `pull_request_review_comment` runs, so that trigger counts, and so do `pull_request_target`, `workflow_run`, and `issue_comment`.
- Every job in a counted workflow counts, whether or not it checks out the branch. A shell step can run the PR title or the branch name through `${{ }}`, and build writes both.
- A job fails the audit when it names a secret other than `GITHUB_TOKEN` through `env`, `with`, `secrets`, or `secrets: inherit`. It also fails on `id-token: write`, on a `runs-on` label that isn't GitHub-hosted, and on a token that can write `contents`, `packages`, `deployments`, or `actions`. The token's permissions are the job's or workflow's `permissions` block, or the repo's default when neither has one. `pull-requests: write` fails a job while the repo lets GitHub Actions create and approve PRs. GitHub counts an Actions approval toward branch protection's required approvals, and no doc says whether a ruleset counts one, so the audit treats it as counting.
- The audit accepts one guard: a job-level `if:` that skips the job when the PR's author is the machine user. A guard on `github.actor` doesn't count. A CodeRabbit comment starts a `pull_request_review_comment` run on the factory's code with CodeRabbit as the actor. An environment whose branch rule shuts out factory branches doesn't count either, because the job then fails on every factory PR, and CI goes red for a reason no build can fix.
- The audit also fails a job when it can't resolve part of it, such as an expression in `runs-on`, `permissions`, `environment`, or a secret's name, or a reusable workflow it can't fetch.
- Setup runs the whole audit under the maintainer's login, and its fixes go into setup's diff and plan (ADR 0017). The machine user's token gets a 403 on the repo's Actions settings and its self-hosted runner list. So before every push, the runner reruns only the rest: the default branch's workflows, the copies on the commit it's about to push, the rulesets, and the environments. It reads the pushed commit's copies too, because a `push` run uses them. Setup reads the settings as `default_workflow_permissions` and `can_approve_pull_request_reviews` from `GET /repos/{owner}/{repo}/actions/permissions/workflow`, and the runners from `GET /repos/{owner}/{repo}/actions/runners`. Setup's reading stands until setup runs again, and the runner applies setup's default to a job with no `permissions` block. So the runner can't see either setting change after setup, such as create-and-approve turned on.
- When the audit fails before a push, the runner doesn't push. The issue pauses with each failing job and its fix, and the answer `retry` reruns the audit and pushes once it passes.
- The machine user's token has no `workflow` scope (ADR 0005), so GitHub rejects a push that adds or edits a workflow file unless another branch holds the same file. A scope limits only a token, so the runner pushes over HTTPS and lets only the machine user's token answer git's credential request. Before every push, the runner diffs the branch from its merge base. A change under `.github/workflows/`, a deletion included, pauses the issue before the push, so a workflow edit never runs before the maintainer reads it. The pause shows the change and names `flight-deck push <issue>`, which pushes build's commit under the maintainer's own login, the way `flight-deck apply` applies a hand run's outbox. The runner counts that push as its own.
- A push test as the machine user on a scratch repo showed where the scope stops. A merge of the default branch that brought in its change to a workflow file pushed, so build's merge of its base works. A deletion of a workflow file also pushed. So the scope doesn't keep a factory branch from dropping a workflow from its own PR, and the pause above does. A new branch at an older commit whose workflow file no branch held was refused. When GitHub refuses a push for the `workflow` scope anyway, such as a `reset` to a commit whose workflow file has since changed on every branch, the issue pauses the same way, for `flight-deck push`. GitHub's refusal reads "refusing to allow a Personal Access Token to create or update workflow `<path>` without `workflow` scope".
- Local actions under `.github/actions/` also run from the branch, and the pause doesn't cover them. Under the rule, a job that checks out the branch holds nothing, so an edited local action unlocks nothing.
- The runner remembers the last commit it pushed to each factory branch and spec branch. Before it takes, lands, marks ready, or flags for review, it compares that commit with the branch on GitHub. A mismatch pauses the issue and names the commit, which could come from a CI job, another tool, or the maintainer. `keep` sends that commit to check, which judges it like any other. `reset` puts the runner's commit back with a force push, the only one the runner makes (ADR 0007). Without the comparison, the runner would start check on a head that build never wrote and that has no claims. After a pause for a rendered file, the maintainer's push doesn't pause the issue: once the answer `rendered` passes the runner's tests, the runner counts the new head as its own push (ADR 0022).
- A job with `statuses: write` can set `flight-deck/check` on any commit, because a required status check can be pinned only to a GitHub App, and the machine user isn't one. The rule allows that write. The maintainer acts on the runner's flag, not on the status.
- Every factory branch starts with `flight-deck/`. An issue's branch is `flight-deck/<issue-id>`, and a spec branch is `flight-deck/spec-<issue-id>`. The prefix is fixed, not a record setting, so every shipped exclusion and setup's trial branch match the same glob.
- Flight Deck ships one entry per host, beside the review bots' done rules (ADR 0016). An entry names the files the host reads, such as `vercel.json`, `netlify.toml`, `wrangler.toml`, `wrangler.json`, `wrangler.jsonc`, `render.yaml`, `railway.json`, `railway.toml`, or Heroku's `app.json`. It also names the GitHub app the host posts statuses, check runs, or deployments as, and a recipe that excludes factory branches. The record names the hosts a repo uses. Research covered Vercel, Netlify, and Cloudflare, so the Render, Railway, and Heroku recipes are still to write.
- A recipe is declarative, such as `"git": { "deploymentEnabled": { "flight-deck/*": false } }` in `vercel.json`, or an inline branch test in `netlify.toml`'s `ignore`. It never calls a script in the repo, because the branch can edit the script. Where the host reads the exclusion from a repo file, setup's diff adds it on the default branch. Where only the host's dashboard holds it, setup's plan names the setting for the maintainer to change.
- Setup's trial PR proves each exclusion. The trial branch starts with `flight-deck/`, and no status, check run, or deployment from a recorded host's app may appear on its head. A host that can't exclude factory branches alone, such as Cloudflare Workers Builds with its one Enable Preview Builds checkbox, gets a proposal to turn its previews off for the whole project. If the maintainer declines, setup doesn't add the factory, the way it refuses two-way sync (ADR 0013). For a host with no shipped entry, setup drafts one from the marks it saw on the last 30 PRs, and the maintainer confirms it, like a review bot with no shipped rule (ADR 0016).
- Before every push, the runner's diff also pauses on a change to any file a recorded host reads, a deletion included. It matches the file name anywhere in the tree, because in a monorepo `vercel.json` can sit in `apps/docs/`. With that pause, the branch can't switch its own host build back on, so an exclusion in a repo file holds as well as one in the dashboard. The CI audit checks that each repo-file exclusion is still on the commit the runner is about to push.
- When a recorded host's app posts a status, a check run, or a deployment on a factory commit anyway, the host build has already run. The runner pauses the issue, names the host and the commit, and tells the maintainer to treat that host's preview secrets as exposed. The answer `retry` waits for the next push. A dashboard change after setup is the same blind spot as the Actions settings above, and this pause is where it shows. The runner doesn't sort apps it has no entry for. Setup's scan of the last 30 PRs does.
- Factory PRs get no preview, so Linear shows none on their issues, and check never waits for a host build on one (ADR 0016). A maintainer who wants a preview deploys the reviewed commit with the host's own tools after reading the diff.
- On Shaders, no job a factory branch starts names a secret. React Doctor's job runs npm in the checkout and holds `pull-requests: write` while create-and-approve is on, so the branch's code could approve its own PR. Changesets needs that setting to open its Version Packages PR with `GITHUB_TOKEN`. The fix gives Changesets a token of its own, used only on pushes to `main`, and then turns the setting off. That keeps React Doctor's comments on the maintainer's own PRs. Shaders has no host, so no dry run tested host builds.
- The rule covers the runner's pushes. A flow the maintainer runs by hand pushes under the maintainer's login, like the rest of ADR 0007's limits.
