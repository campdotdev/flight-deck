# Flight Deck ships each review bot's done rule, and the repo record names the bots

The bot round waits for each review bot the repo record lists. The runner needs one rule per bot to tell when that bot has finished with the head commit (ADR 0010), because no two bots leave the same done mark. Copilot posts a review, CodeRabbit sets a commit status, and Codex edits a comment whose hidden marker differs between repos. These rules describe vendors, not repos. So they ship with each Flight Deck version as data the runner reads, beside the flows and skills, and they change only through `flight-deck update` (ADR 0015). The record keeps the repo's choices: which bots to wait for, each bot's time limit, and whether the runner has to ask a bot to review. It can also hold a full rule of its own, for a bot Flight Deck doesn't ship or to replace a shipped rule that broke. A reviewer counts as a review bot only if it waits for the PR to go ready or for a mention. Anything that has already run on the draft when check starts is CI, whatever it posts, so check's first verdict judges it. A ready-only job, a job in the repo's own workflows that runs only once the PR is ready, is CI too unless the record lists it as a review bot, and the bot wait waits for it (ADR 0010).

## Considered options

- **Setup copies each rule into the record,** the way it writes slot defaults. The record would show exactly what the runner does. But a vendor change would break every repo until each one reran setup and committed the result. Slot defaults are the repo's choices. A rule is knowledge about a vendor, like the text of a skill, which also ships in the version folder (ADR 0014).
- **Rules ship only with Flight Deck.** A bot Flight Deck doesn't know, such as an in-house reviewer, would wait for a new version. So would the fix for a rule a vendor broke.
- **A commenting workflow, such as React Doctor, is a review bot.** Its findings would reach check only in the bot round, after check had passed a commit whose findings existed before check started. Every PR with a finding would cost a bot round and a trip back. Its login, `github-actions[bot]`, is also shared by every workflow in the repo.

## Consequences

- A rule holds six fields:
	- `login`, the account whose reviews and comments are the bot's.
	- `done`, one done mark on the head commit. A `check_run` matches by name and app, and the newest run wins. A `status` matches by context and state. A `review` is one by `login` whose `commit_id` is the head. A `comment` is the newest one by `login` that contains the head SHA, full or short, and a set text.
	- `reviewed`, what the done mark, or a second mark on the head, must show to count as a review.
	- `findings`, where the bot's findings appear. Every rule has `inline`. A bot that also writes findings in the review body adds `review_body`, such as CodeRabbit for its nitpicks and Sourcery for its overall comments.
	- `retrigger`, a comment to post or a new review request.
	- `time_limit`, a default the record can override.
- A done mark counts as a review only when it matches the rule's `reviewed` test. Anything else reads "didn't review", and the ledger quotes the bot's own words. A reworded success text makes the ledger understate the bot's reviews, never overstate them, and the bot's findings still reach the bot round. A done mark that reads "didn't review" is never a finding itself, so Copilot's out-of-quota review starts no bot round.
- Every mark a rule reads, the done mark or one a `reviewed` test names, must come from the bot itself. A `status` counts only when its creator is the rule's `login`. A check run from the shared `github-actions` app counts only when no workflow file under `.github/workflows/` made it, which is how Copilot's run appears. The repo's own workflows run code from the PR's branch, and their token can post a status or a check run with any name, so without this a factory branch could fake a bot's review and end the wait before the bot's real findings arrive (ADR 0025).
- A done mark counts only if the bot made it after the runner last marked the PR ready. An older mark on the same head reads as not done yet. Without this, a PR that check passes again on an unchanged head would start its bot round before any bot reviewed again, with findings an earlier round already judged.
- The record lists each bot as a `[[review_bots]]` entry. Every record entry names a shipped rule with `rule` or holds a full one under its own `name`. A record rule under a shipped name replaces the shipped rule. Every entry sets `ask`, because the record never assumes a default (ADR 0003). Either kind of entry can set `time_limit`, and a `rule` entry without one keeps the shipped rule's. An entry with neither `rule` nor `name` makes the record invalid. Setup won't write one, and the runner pauses the issue with the error. A bot that leaves no done mark stays out of the record, and the maintainer reads its comments on the PR.

	```toml
	[[review_bots]]
	rule = "copilot"
	ask = false
	time_limit = "20m"

	[[review_bots]]
	name = "acme-reviewer"
	login = "acme-review[bot]"
	done = { kind = "check_run", name = "Acme Review", app = "acme-review" }
	reviewed = { conclusion = ["success", "failure"] }
	findings = ["inline"]
	retrigger = { comment = "/acme review" }
	time_limit = "15m"
	ask = false
	```

- With `ask = true`, the runner sends a bot's re-trigger every time it marks the PR ready, including the first time. This covers CodeRabbit on a public repo with fewer than 10 stars, Greptile when it's set to manual, and Gemini unless marking a PR ready starts its review. `ask` can name a merge-risk level instead, such as `ask = "high"`. The runner then sends the re-trigger only when check's passing verdict rates the change at that level or above (ADR 0020), and the bot round waits only for the bots it asked. A maintainer who asks a paid bot only on larger changes keeps that habit, and the other PRs don't wait out the bot's time limit.
- v1 ships rules for Copilot, Codex, CodeRabbit, Greptile, Sourcery, Cursor Bugbot, Claude Code Review, Qodo, and Gemini. They read these marks on the head:
	- Copilot's done mark is its review, from `copilot-pull-request-reviewer[bot]`, which lands seconds after its check run finishes. The review counts only when the `copilot-pull-request-reviewer` check run from the `github-actions` app concluded `success`, because Copilot also posts a review when it reviewed nothing, such as out of quota. Its re-trigger is a new review request.
	- Codex's done mark is the summary comment that `chatgpt-codex-connector[bot]` edits in place. Codex is done when the comment's hidden `codex-review-state:v1` block has `code_review.commit_sha` at the head and `code_review.status` at `completed`. The rule also accepts the form on Shaders, a `<!-- codex-pull-request-review-summary -->` marker with a short SHA. Its re-trigger is `@codex review`.
	- CodeRabbit's done mark is its `CodeRabbit` commit status. Only `success` with the description "Review completed" counts, because `success` also covers "Review rate limited" and "Review skipped". Its re-trigger is `@coderabbitai review`, which also ends its pause at 5 reviewed commits.
	- Greptile's done mark is the `Greptile Review` check run from the `greptile-apps` app. `success` and `failure` count, and `failure` means the confidence score fell below the repo's minimum. Its re-trigger is `@greptileai review`.
	- Sourcery's done mark is the `Sourcery review` check run from the `sourcery-ai` app, because its review's `commit_id` can trail the head. `success` and `failure` count. Sourcery posts `skipped` after 5 automatic re-reviews on a PR, and its re-trigger, `@sourcery-ai review`, resets that count.
	- Cursor Bugbot's done mark is the `Cursor Bugbot` check run from the `cursor` app. `success` and `failure` count. `neutral` covers findings but also a cancelled or failed run, such as on a usage limit, so it counts only when the summary reads "Bugbot completed review" or counts the issues found, such as "found 1 potential issue". Its re-trigger is `cursor review`.
	- Claude Code Review's done mark is the `Claude Code Review` check run from the `claude` app. Its conclusion never tells a review from a skip, so only a title that starts "Code review found" counts. Its re-trigger is `@claude review`.
	- Qodo's done mark is the newest comment from `qodo-code-review[bot]` that reads "Code review by qodo was updated up to the latest commit" and links the head's full SHA. Qodo posts no check run or status.
	- Gemini's done mark is a review from `gemini-code-assist[bot]`, because its app can't write checks or statuses. Its re-trigger is `/gemini review`.
- Codacy, SonarQube Cloud, and Graphite run on drafts and on every push, so the record lists them as CI-only extras, like React Doctor. A CI-only extra that reports through comments names its comment markers, such as React Doctor's `<!-- react-doctor:summary -->` and `<!-- react-doctor:review -->`. Setup maps each `github-actions[bot]` comment marker it finds to its workflow. The runner copies those comments on the head into check's inbox as that extra's output.
- Gemini Code Assist reviews a PR when it opens, drafts included, because `code_review.pull_request_opened.include_drafts` defaults to `true`. After that, it reviews only when asked with `/gemini review`. It can't be a CI-only extra. It leaves no check run or status, so check doesn't wait for its review, and it never reviews a later push on its own. So for a repo that uses Gemini, setup's uncommitted diff sets `include_drafts: false` in `.gemini/config.yaml`, and Gemini stays a review bot. The setting has no author filter, so the maintainer's own drafts lose Gemini's review at open too, and setup's plan says so. Setup's test PR shows whether marking a PR ready starts a Gemini review on its own. If it does, the record sets `ask = false`, so Gemini doesn't review the PR's first ready twice. On later readies the runner re-triggers it anyway (ADR 0010), and a doubled review costs only a repeated finding, which the bot round judges. Otherwise it sets `ask = true`.
- If the maintainer declines the `include_drafts` change, setup leaves Gemini out of the record and says what that costs. Gemini still reviews each factory draft when it opens, nobody judges that review, and the runner leaves its threads open for the maintainer.
- A host build is CI, but only the maintainer's own PRs get one. A factory branch never gets a host build (ADR 0025), so check never waits for one on a factory PR.
- Some failing checks leave check nothing to read. An app that reports only a commit status shows check only that status's one-line description, because the detail sits on the app's dashboard behind the maintainer's login. The runner can't rerun such a check the way it reruns a failed workflow. If one of the record's commands, such as the build, reproduces the failure, check sorts it like any failing command. If none does, check pauses the issue at once and links the check's page, because only the maintainer can read the cause.
- If one listed bot doesn't review the head on 3 PRs in a row, for any reason, the runner files one unsent issue and flags it, with a title such as "Copilot didn't review the last 3 PRs". The issue quotes what the bot left on each head, or says it left nothing. The runner still waits for the bot on later PRs. A broken rule surfaces there.
- Setup finds a repo's bots in five steps:
	1. It reads each shipped bot's config files, such as `.coderabbit.yaml`, `greptile.json`, and `.cursor/BUGBOT.md`.
	2. It reads the last 30 PRs, collects each login and app outside the repo's workflows that left a review, check run, status, or comment, and matches each one to a shipped rule.
	3. It sorts each one by the timing test. An app that acted on drafts or on every push becomes a CI-only extra. A bot whose every review followed a mention gets `ask = true`.
	4. It proposes each bot with its evidence, and preselects a bot only if it reviewed one of the last 10 PRs. It also lists the shipped rules it saw no trace of.
	5. For a bot with no shipped rule, it drafts a rule from the marks the bot left, and the maintainer confirms the draft or leaves the bot out.
- Setup tests each bot it lists on a PR the machine user opens, because a bot can ignore the machine user even when it reviews the maintainer's PRs. Once the maintainer confirms setup's plan and the machine user has its access, setup opens a draft PR from a throwaway branch, marks it ready, sends each bot's re-trigger, and waits out each bot's time limit. The same PR proves each `artifact` entry for rendered files, so setup also waits for its CI (ADR 0022). Then it closes the PR and deletes the branch. A bot that reviews stays in the record. A bot that doesn't is left out, so no factory PR waits for it. Setup says why and names what the vendor needs as an optional step, such as the machine user's own plan or seat. Flight Deck never requires one. On Shaders, Copilot reviewed the machine user's PRs only once the machine user had its own Copilot plan. Greptile skipped the PRs `flightdeckbot` opened, though it answered a mention from `flightdeckbot` on the maintainer's PR.
- When setup writes a rule that shadows a shipped one, it offers an upstream report, the same prefilled Flight Deck issue link that debrief uses (ADR 0012). Rerunning setup lists each record rule that shadows a shipped one and offers to drop it, in the same diff as the new defaults.
