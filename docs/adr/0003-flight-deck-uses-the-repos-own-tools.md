# Flight Deck uses the repo's own tools and requires none of them

Flight Deck needs only its own platform: macOS, Claude Code, git, GitHub with `gh`, and Linear, plus Node and Chrome for a repo with a web app (ADR 0009). Every other tool a factory runs comes from the repo. Setup finds the tools the repo already uses and writes them into the repo record, a TOML file committed at `.flight-deck/record.toml`. Commands go into optional categories, one command per category: types, lint, format, unit, integration, and E2E. The dependency install has its own category, `dependencies` (ADR 0018). Other checks, such as Fallow or React Doctor, go into a list of extras, and skills fill slots. Each command and extra is marked to run locally or only in CI. Flight Deck never installs a tool into a repo or adds one to the repo's dependencies. When a repo lacks something, such as unit tests, setup offers an issue that describes the gap and leaves the choice of tool to plan.

## Considered options

- **The board's stack.** The board was drawn for one React component library, and its flows name Vitest, Storybook, Playwright, Fallow, React Doctor, Figma, and changesets. A fixed stack would let each flow run deeper checks written for those tools. Every repo outside that stack would have to adopt them or go without a factory.
- **A switch for each step Flight Deck knows.** A repo on a stack Flight Deck doesn't know would wait for a new Flight Deck version.
- **Steps written only in the repo's `AGENTS.md`.** Nothing would prove a step ran, so check couldn't hold build to it.

## Consequences

- The record holds no credential. Each session reads it at the commit its worktree starts from (ADR 0002). A change to the repo's tools edits the record in the same diff, and a diff that touches the record pauses the issue before check (ADR 0007). Setup checks the record against a schema Flight Deck ships, and the runner checks it before every session. An invalid record pauses the issue with the error. Facts about one Mac, such as the concurrency cap and the repo list, stay out of the record.
- For a repo with an app, the record holds a start command that takes a port, the URL to load, and a signal that the app is ready. The runner gives each session its own port. If setup can't start the app on a port other than its default, the record marks the app single-instance, and the runner runs only one session of that repo at a time.
- Plan offers two slots: `reproduce`, which runs on a bug, and `design`, which runs on a change users see. Build offers `finish`, which runs once every criterion passes and before build merges its base. Check offers `review`, which runs after check's own review. Each slot holds an ordered list of skills. `reproduce` defaults to `reproducing-bugs` (ADR 0014), and the other three stay empty unless setup finds a skill for them. Setup writes Flight Deck's default skill for each slot into the repo record, and the maintainer adds, removes, or reorders skills there. It also writes each stage's time limit that way, with defaults of 30 minutes for plan, 90 for build, and 45 for check. Because the defaults are written out, a new Flight Deck version never changes what a repo runs without a diff in the repo. Each slot skill decides whether the change needs it and says so in the handoff, such as "no changeset: docs-only change".
- If the record leaves a field out, the factory pauses the issue instead of assuming a default. A gap is written down as a gap. Setup stops only for what ADRs 0005, 0013, and 0017 name, such as a repo with no GitHub remote or a dependency install that fails. The flows work around any other gap. Build's claims say "type check only" or "unproven", and check waits for no CI the repo lacks.
- When the repo's `CLAUDE.md`, `AGENTS.md`, or hooks conflict with a flow, the flow owns the mechanics: which tool commits and when, the branch, pushes, the PR's draft state, Linear writes, the handoff, and when to stop for the maintainer. A stage stops only by pausing, so a repo rule that stops work mid-stage for a person loses. The repo owns everything else, including the format of what the factory writes, such as Conventional Commits, commit trailers, and its PR template. Setup lists each conflict it finds, and the maintainer settles each one once in the record. Every flow, including one run by hand, reads the record right after the take and follows those answers. A session that meets a conflict setup missed pauses the issue.
- Setup turns each review step the repo's instructions prescribe, such as Shaders' `/code-review`, into an extra or a slot skill, so check runs it. Factory sessions load none of the maintainer's user-level skills (ADR 0002), so setup lists each one the repo's instructions call, and the maintainer maps it to a slot or tells the factory to skip it.
- Flight Deck writes no `story` skill. Setup proposes a Storybook repo's own story skill for `finish` when the repo has one (ADR 0014).
- Flight Deck writes `design-check` for plan's `design` slot and check's `review` slot. It reads only the design, and finds frames in this order: the frames the maintainer linked, then Code Connect's map when the record says the repo uses it, then the pages the record names. No Figma tool searches frames by name, so it matches names itself in each page's layer outline from `get_metadata`, one call per page. When Figma refuses a call for its per-minute limit, it waits a minute and retries once. Any other Figma failure, such as a spent daily limit or a frame image it can't download, pauses the issue with that reason and never becomes "design not checked".
- In plan, `design-check` lists only the states the change creates or alters: the states the criteria name, plus the empty, loading, and error states of a new screen that loads data. A frame or a component variant covers a state, and so does a rule the design defines, such as a dark-theme variable mode or a component the change reuses as it is.
- In check, `design-check` compares the running app with exactly the frames the brief's Design part names, read fresh, and a named frame that no longer exists pauses the issue. It runs the find step itself only when the brief has no Design part. It reads each frame's variables, copy, element order, and layout with `get_design_context` and `get_variable_defs`, and the app's computed styles and DOM, at the frame's width and in its state, with `browser_evaluate` (ADR 0009). A value bound to a variable matches only exactly, or through the repo token the variable maps to. A raw size matches within 2px, and a raw color matches when nobody could see the difference. Placeholder content, images, and font rendering never count. A finding names the frame's link, the stated value, and the app's value, and its failing case is the screenshot pair. `get_screenshot` returns a short-lived URL, so the session downloads the frame's PNG into its outbox with `curl`, from the record's `image_host`. A state check can't put the app into, such as a server error, is "not compared". It sends no finding, and the slot's line in the verdict lists those states first.
- Flight Deck writes a `changeset` skill for build's `finish` slot, and setup proposes it only when the repo has a `.changeset/` folder. The skill takes each bump from the brief's Key interfaces under the record's convention (ADR 0017), and only the packages from the diff. An accepted break and an added public contract get the bumps the convention names, and anything else is a `patch`. If the diff reads as a break the brief didn't accept, the bump stays where the brief puts it, and build pauses. No bump takes a package to its first major. A break counts against the last release, which the skill finds from the latest release tag and the changesets pending at the base. A change to a contract added since then amends the pending changeset that added it. In a repo whose release tooling reads commit messages instead, build marks the commit (ADR 0027), and check holds that commit to the same rules.
- Only a change the package's users would notice gets a changeset: behavior, exports or types, dependencies, or performance the brief set out to change. Each such change gets its own changeset, which lists only published packages that aren't ignored and whose users see the change, never dependents or other members of a `fixed` group. When the record's `ci_requires_changeset` is `true`, any other change gets `changeset add --empty`. The skill writes the files by hand, because Changesets v2 runs `changeset add` without prompts only with `--empty`. It confirms every bump and resulting version from the release plan that `changeset status --output <file>` writes. The text takes the voice of the repo's 10 or so newest changelog entries, unless the repo's docs say otherwise, and carries only the brief's Summary and Desired behavior, with no links. At every handoff, build reverts the branch's changeset edits and the skill writes them again. Check sends a finding for a missing changeset, a wrong bump under the convention, a first major, a listed package the diff doesn't change, or text that misstates the change. The failing case quotes the brief line or the convention beside the changeset line.
- A Flight Deck dependency that acts on every session, such as a plugin's hooks, can't be forced into the maintainer's own Claude Code sessions. The runner decides what each factory session loads.
- Flows rely on no command the platform lacks or blocks. macOS has no `timeout` command, and Claude Code blocks a foreground `sleep`.
- Linear is the only tracker in v1. Flows reach it through named operations, and the runner's tracker code sits behind one interface, so another tracker can come later without new flows.
