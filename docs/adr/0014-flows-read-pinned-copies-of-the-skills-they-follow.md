# Flows read pinned copies of the skills they follow

Flight Deck's flows follow skills that other authors wrote: Matt Pocock's skills, pstack, ponytail, and Warp's `common-skills`. Those upstreams change often. Matt Pocock removed `resolving-merge-conflicts` on 2026-09-24, and a version range can't resolve against his tags. If a flow followed the latest upstream, check could judge two commits of one repo by different rules, and a third party could change what a session with commit access does without anyone reading the change. So every skill a factory session follows sits in Flight Deck's repo at a known commit, except a skill the repo keeps in its own `.claude/skills/`. It is a copy of an upstream skill, a fork that opens with a comment naming its upstream path, its commit, and what changed, or Flight Deck's own text. An upstream change reaches a factory only in a new Flight Deck version, after someone reads the diff. Flows read each skill's `SKILL.md` as a file and follow it instead of invoking it, because several of the skills, such as `to-spec`, `to-tickets`, `technical-writing`, and `unslop`, set `disable-model-invocation: true`. A session can't invoke a skill with that flag, and a subagent can't preload one.

## Considered options

- **Depend on the upstream at run time,** through a plugin `dependencies` entry or `ctx7 skills install`. Fixes would arrive without a new Flight Deck version, but the version would float, and `claude-plugins-official` updates plugins automatically by default.
- **Ship registered, namespaced skills,** such as `flight-deck:tdd`, that flows invoke through the Skill tool, with the flag removed in each fork. Every fork would then appear in the maintainer's own sessions wherever Flight Deck is installed, beside the maintainer's own `tdd`.

## Consequences

- Flight Deck's copies and forks are files beside the flows, not registered skills. The runner hands each flow the path of every slot skill the repo record names, and the flow reads it the same way. The hand-run `/flight-new` reads Flight Deck's copies under `~/.local/share/flight-deck/current/`, never the maintainer's own copies, because only Flight Deck's forks file issues in the factory's statuses.
- The one exception is a skill the repo keeps in its own `.claude/skills/`, which the repo record can name in a slot. The session reads it at the commit it works on, so the repo's own history pins it. Flight Deck neither copies nor reviews it.
- A skill whose plugin adds hooks, such as ponytail, runs without them. All of ponytail's rules are in its `SKILL.md`, and its hooks only inject that text again at each prompt and subagent.
- Flight Deck's repo is MIT. One `CREDITS.md` at the root holds each upstream's full MIT notice and the commit Flight Deck copied. It also holds Siqi Chen's notice for humanizer, whose pattern list `unslop` follows, and HumanLayer's for `show-me`, linked to `humanlayer/skills`, because both Warp forks borrow from Matt Pocock's `pr`, which credits `show-me`. It carries the Apache-2.0 license and NOTICE of the Playwright MCP that each version bundles (ADR 0015). When Flight Deck's own text borrows a rule, the credit goes in `CREDITS.md`, not in the skill, so sessions spend no tokens on it. Flight Deck copies only from an upstream whose license lets a public repo redistribute it.
- Flight Deck never installs skills with `ctx7`. Context7's MCP server is a docs source for plan and build that setup offers and the maintainer opts into. The record then lists only its `resolve-library-id` and `query-docs` tools. Flows work without it, because WebFetch reaches documentation sites (ADR 0007).
- Fork a skill when Flight Deck keeps the upstream's steps. Write Flight Deck's own text when it keeps only a rule or two, or blends several sources.
- Flight Deck copies these skills unchanged:
  - `technical-writing` and `unslop`, from pstack (`cursor/plugins`) at `d457567`. Every flow reads both before it writes text a person reads, and so do `/flight-issue` and `/flight-new`.
  - `ponytail`, for plan and build, and `ponytail-review`, for check's bugs-and-simplicity reviewer, from `DietrichGebert/ponytail` at `09c434a`.
  - `writing-for-agents`, `grilling`, and `domain-modeling`, from `mattpocock/skills` at `49dd158`. Build reads `writing-for-agents` whenever its diff touches `CLAUDE.md`, `AGENTS.md`, `CODING_STANDARDS.md`, or a `SKILL.md`. `/flight-new` follows the other two.
- Flight Deck forks these from `mattpocock/skills` at `49dd158`, unless a line names another upstream:
  - `reproducing-bugs`, from `diagnosing-bugs`, for plan's `reproduce` slot. It keeps the redaction rule and Phases 1 and 2, drops Phases 3 to 6, the HITL script, and upstream's three asks of a person, and follows plan's reproduction rule instead (ADR 0026).
  - `tdd`, with `tests.md` and `mocking.md`, for build (ADR 0027).
  - Plan's brief template, from `triage/AGENT-BRIEF.md`, without its Category field or its pull request example (ADR 0026).
  - `standards-review`, from `code-review`, for check's standards reviewer (ADR 0028).
  - `to-spec` and `to-tickets`, for `/flight-new` (ADR 0013). They file in the factory's statuses instead of applying the `ready-for-agent` label, and Flight Deck's Linear operations replace the tracker doc and the pointer to `/setup-matt-pocock-skills`. `to-spec` still checks the seams with the maintainer, and `to-tickets` still waits for approval of the breakdown.
  - `write-pr-description` and `merge-risk`, from `warpdotdev/common-skills` at `8792394`, for build's PR body and check's merge risk (ADR 0020).
- Flight Deck writes `flight-issue`, `design-check`, and `changeset` itself. It ships no upstream skill besides the copies and forks above. Its own text borrows rules from skills it doesn't ship, credited in `CREDITS.md`: build's from `resolving-merge-conflicts` at `153fc1b` and pstack's `principle-attack-the-premise`, check's from pstack's `principle-test-behavior-not-implementation` and `interrogate`, and debrief's from Matt Pocock's `retro` and pstack's `correct`.
