# The factory writes on a PR only what a person would

In the FlutedGlass dry run on Shaders, the runner posted the spec check's verdict and the bot round's verdict on the PR as comments. The spec check's comment ran to 10,615 characters of criterion numbers, sub-issue identifiers, commit hashes, and five absolute paths under the maintainer's home folder. The `flight-deck/check` status carried a session ID. The bot round dismissed both of Copilot's findings in a top-level comment and left both threads open. The maintainer found the PR almost impossible to read. So `flightdeckbot` now writes on a PR only what a person who opened it would: the body and its images, the `flight-deck/check` commit status, ready and draft changes, review requests, a review bot's re-trigger comment when its done rule needs one, and a reply in each review bot's thread. Check's verdict reaches the PR only as the status, as "What does a factory PR show the maintainer?" decided, and check's findings stay in Linear. The maintainer starts review from the "Needs your review" flag in Linear, which now carries a merge risk that the runner computes from check's ratings.

## Considered options

- **A summary comment for each verdict, or one comment the runner edits at each verdict,** in ADR 0019's shape. CodeRabbit, Greptile, and the prototype runner all post one. The "Needs your review" flag already carries the status line and the summary. GitHub emails the repo's watchers about every comment, and strangers and review bots read the PR too. A verdict comment gives a bot something to argue with.
- **Check's findings as line comments on the draft,** the way CodeRabbit leaves them. A finding on its line reads better than `path:line` in Linear. But findings land while nobody reads the draft, and each round leaves threads behind. Build still reads findings from Linear, and a finding about a criterion or about the body has no line.
- **Build rates merge risk in the body.** Build would grade its own work.
- **An interactive walkthrough of each PR,** from Warp's `pr-walkthrough`. A session can't check that the page renders, because Chromium can't start from sandboxed Bash, and the browser MCP server's dead proxy blocks the D3 script from its CDN. A link on the PR would also need a public host, which a private repo can't use.

## Consequences

- The bot round writes a reply in each bot thread and nothing at the top level. For a finding it dismisses, check writes one or two sentences that a stranger can follow. The runner posts them and resolves the thread. A finding that check sends back gets no reply until check passes the commit that fixes it. The runner then replies "Fixed in <short SHA>." and resolves the thread. A finding that pauses the issue gets no reply, and its thread stays open. The factory never replies to a person's comment on its PR.
- Nothing the factory posts on a PR carries a Linear identifier or URL unless the repo's PR rules ask for one, because the branch name already links the PR to its issue. Issues are named by title, and only when a reader needs the name. Code is cited by a reply on its line or by a GitHub permalink in the body, never by a local path. Session IDs, runner versions, footers, and outbox file names stay out. Check treats a Linear identifier in the body like any other misstatement in the body.
- The runner's scan of everything it sends to GitHub gains two patterns: an absolute path under the Mac's home folder or Flight Deck's folders, and a session ID. A hit fails the outbox like any other broken rule, so the stage gets its one retry and pauses after a second failure. A credential still pauses the issue at once (ADR 0007). Linear comments keep the runner's footer and its session ID in their `Details` fold (ADR 0019).
- The `flight-deck/check` status uses ADR 0019's status phrases without the dot, plus a count, such as "Passed check: 26 criteria proven", "Back to build: 2 findings", and "Passed the bot round: 2 bot findings dismissed". The runner sets the status to `pending`, with "Checking", when check takes a commit.
- Build writes every body under a fork of Warp's `write-pr-description` (MIT), which replaces Matt Pocock's `pr`. The repo's PR rules outrank the fork, and the fork fills in where they're silent. For a repo with no rules, the body has an opening paragraph, a `## Review guide` when one is warranted, `## What changed`, and `## Validation`. The fork reads the brief and the claims instead of commit messages, and it drops upstream's issue-link rule and prose section. It borrows one line from `pr`: a short diagram or diff sketch when that shows the change faster than prose. The review guide's one-way doors and blast radius replace `pr`'s Merge Danger, and check still sends back a body that understates either.
- Build on the spec takes fresh before-and-after screenshots of the spec branch. The runner also puts every screenshot that the sub-issues' build and check sessions took in its inbox, each labeled with the commit it shows. When build on the spec can't take its own, it picks from those and prefers images that no later landing changed. Images are the only part of a body that may come from check. The words stay build's own.
- Check rates merge risk under a fork of Warp's `merge-risk` (MIT) on every verdict that ends in "Needs your review": a passing check of a standalone issue, the spec check, and the bot round. A sub-issue's check skips it. The fork keeps Warp's five categories, weights, and thresholds, and it judges each category from check's own evidence instead of the PR alone. Check writes the five ratings in its outcome, and the runner computes low, medium, or high, so every repo uses the same weights. The level and the riskiest category go in the gist of the "Needs your review" status line, such as "🟡 Needs your review: medium merge risk, two hooks renamed". The categories and their gaps go in the part for the maintainer. Merge risk never pauses or blocks an issue.
