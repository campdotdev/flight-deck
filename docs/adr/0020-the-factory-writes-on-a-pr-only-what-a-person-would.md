# The factory writes on a PR only what a person would

In the FlutedGlass dry run on Shaders, the runner posted the spec check's verdict and the bot round's verdict on the PR as comments. The spec check's comment ran to 10,615 characters of criterion numbers, sub-issue identifiers, commit hashes, and five absolute paths under the maintainer's home folder. The `flight-deck/check` status carried a session ID. The bot round dismissed both of Copilot's findings in a top-level comment and left both threads open. The maintainer found the PR almost impossible to read. So the machine user now writes on a PR only what a person who opened it would: the body and its images, the `flight-deck/check` commit status, ready and draft changes, review requests, a review bot's re-trigger comment when its done rule needs one, and a reply in each review bot's thread and in each of the maintainer's threads that build acted on (ADR 0023). Check's verdict reaches the PR only as the `flight-deck/check` status, and check's findings stay in Linear. The maintainer starts review from the "Needs your review" flag in Linear, which now carries a merge risk that the runner computes from check's ratings.

## Considered options

- **A summary comment for each verdict, or one comment the runner edits at each verdict,** in ADR 0019's shape. CodeRabbit, Greptile, and the prototype runner all post one. The "Needs your review" flag already carries the status line and the summary. GitHub emails the repo's watchers about every comment, and strangers and review bots read the PR too. A verdict comment gives a bot something to argue with.
- **Check's findings as line comments on the draft,** the way CodeRabbit leaves them. A finding on its line reads better than `path:line` in Linear. But findings land while nobody reads the draft, and each round leaves threads behind. Build still reads findings from Linear, and a finding about a criterion or about the body has no line.
- **Build rates merge risk in the body.** Build would grade its own work.
- **An interactive walkthrough of each PR,** from Warp's `pr-walkthrough`. A session can't check that the page renders, because Chromium can't start from sandboxed Bash, and the browser MCP server's dead proxy blocks the D3 script from its CDN. A link on the PR would also need a public host, which a private repo can't use.

## Consequences

- The bot round writes a reply in each bot thread and nothing at the top level. Its verdict carries one reply for each finding it dismisses, in one or two sentences that a stranger can follow. The runner posts each reply and resolves the thread. A finding that check sends back gets no reply until check passes the commit that fixes it. The runner then replies "Fixed in <short SHA>." and resolves the thread. A finding that pauses the issue gets no reply, and its thread stays open. The factory replies to a person's comment on its PR only in a thread the maintainer started, once check passes the commit that answers it (ADR 0023). It never replies to anyone else.
- Nothing the factory posts on a PR, the status's Details link included, carries a Linear identifier or URL unless the repo's PR rules ask for one. The branch name carries the issue's identifier, so Linear already links the PR to its issue. In every repo, build writes the body in its own words from the brief, because a private repo can go public and keep every PR it ever had. It never quotes the report, and it never copies or links a Linear attachment. Issues are named by title, and only when a reader needs the name. Code is cited by a reply on its line or by a GitHub permalink in the body, never by a local path. Session IDs, runner versions, footers, and outbox file names stay out. Check treats a Linear identifier in the body like any other misstatement in the body.
- The runner's scan of everything it sends to GitHub gains two patterns: an absolute path under the Mac's home folder or Flight Deck's folders, and a session ID. A hit fails the outbox like any other broken rule, so the stage gets its one retry and pauses after a second failure. A credential still pauses the issue at once (ADR 0007). Linear comments keep the runner's footer and its session ID in their `Details` fold (ADR 0019).
- The `flight-deck/check` status uses ADR 0019's status phrases without the dot, plus a count, such as "Passed check: 26 criteria proven", "Back to build: 2 findings", and "Passed the bot round: 2 bot findings dismissed". An unproven criterion shows in the count, as in "Passed check: 4 of 5 criteria proven". The runner sets the status to `pending`, with "Checking", when check takes a commit. It then sets `success` when check passes the commit, or `failure` when check sends work back. A sub-issue's commit gets its own status too, so each landed commit in the spec PR's Commits tab shows its verdict.
- Build writes every body under a fork of Warp's `write-pr-description` (MIT), which replaces Matt Pocock's `pr`. The repo's PR rules outrank the fork, and the fork fills in where they're silent. For a repo with no rules, the body has an opening paragraph, a `## Review guide` when one is warranted, `## What changed`, and `## Validation`. `## Validation` reports build's own proof, with before-and-after screenshots for a visible change. The review guide's "where you're unsure" comes from the claims' unverified items and shortcuts. The fork reads the brief and the claims instead of commit messages, and still verifies what it carries over. It drops upstream's issue-link rule. It also drops upstream's prose section, because `technical-writing` and `unslop` already govern the body's prose (ADR 0014). It borrows one line from `pr`: a short diagram or diff sketch when that shows the change faster than prose. The review guide's one-way doors and blast radius replace `pr`'s Merge Danger, and check still sends back a body that misstates the change or understates either.
- Setup records where the repo's PR rules live, such as `.github/pull_request_template.md`, a doc like Shaders' `docs/agents/pull-requests.md`, or a paragraph in `AGENTS.md`, or records that there are none. Build follows the rules for the title too. Where they say nothing about the title, build writes it from the brief, in the imperative. Setup flags a template section that build can't fill truthfully, such as a test plan or a "Tested on mobile" checkbox, as a conflict. The maintainer settles once whether build fills it from its claims or leaves it out. Build never ticks a box it didn't verify.
- The spec PR's body describes the whole change grouped by concept, not by sub-issue, because a list of sub-issues would put planning structure on a public PR. Build on the spec takes fresh before-and-after screenshots of the spec branch. The runner also puts every screenshot that the sub-issues' build and check sessions took in its inbox, each labeled with the commit it shows. When build on the spec can't take its own, it picks from those. It prefers images that no later landing changed, and check's over build's, because check took its screenshots on the commit it passed. Images are the only part of a body that may come from check. The words stay build's own.
- The factory writes nothing about a preview deployment, on the PR or in Linear. The repo's host posts its own link on the PR. Linear's GitHub integration reads that link from the PR body or the host bot's comment, and puts a preview shortcut on the linked issue for Vercel, Netlify, Cloudflare, and AWS Amplify. Only Vercel reports the preview for an exact commit through GitHub's deployments API, so a link in the "Needs your review" flag would need a rule for each host to repeat what Linear already shows. The repo record has no field for previews, and setup offers no gap issue for a repo without them. A repo that adds a host later gets previews on its issues with no change to the record.
- Check rates merge risk under a fork of Warp's `merge-risk` (MIT) on every verdict that ends in "Needs your review": a passing check of a standalone issue, the spec check, and the bot round. A sub-issue's check skips it. The fork keeps Warp's five categories, weights, and thresholds, and it judges each category from check's own evidence instead of the PR alone. Alignment covers the changes the brief didn't ask for and the decisions the brief inferred that nobody wrote down. Impact covers blast radius, any break the brief accepts, and any change to auth, permissions, payments, personal data, secrets, migrations, dependencies, infrastructure, or configuration. Verification covers criteria proven only by a type check or taken from an earlier check without being proven again, anything build couldn't verify, and a visible change with no screenshots in the PR. Rollback cost covers one-way doors, such as a released rename or a migration that drops data. Error detection covers whether a failure in production would surface, and is N/A for a library. Check writes the five ratings in its outcome, and the runner computes low, medium, or high, so every repo uses the same weights. The level and the riskiest category go in the gist of the "Needs your review" status line, such as "🟡 Needs your review: medium merge risk, two hooks renamed". The categories and their gaps go in the part for the maintainer. Merge risk never pauses an issue or stops its merge.
