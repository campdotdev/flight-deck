# Flight Deck installs from a script into versioned folders and updates only by hand

Flight Deck ships a runner that launchd keeps alive, so a Claude Code plugin can't install it on its own (ADR 0002). Instead, one command installs Flight Deck: `curl -fsSL https://github.com/campdotdev/flight-deck/releases/latest/download/install.sh | sh`. The script checks for Apple Silicon, downloads one version's tarball from GitHub Releases, checks its SHA-256, and unpacks it into `~/.local/share/flight-deck/versions/<version>/`. The tarball holds everything that version runs: the runner, compiled from TypeScript with Bun into one binary, the menu bar app (ADR 0024), every flow and skill file, a pinned Playwright MCP with its dependencies, a pinned `sandbox-runtime` for refreshing dependency caches (ADR 0018), and a pinned Betterleaks binary. It also carries `LICENSE` and `CREDITS.md` (ADR 0014), because each upstream's notice must ship with every copy. A `current` link names the version in use, and `~/.local/bin/flight-deck` links to its binary. The script then runs `flight-deck install`. Nothing updates on its own. A new version changes what every factory session does, so it reaches a Mac only when the maintainer runs `flight-deck update`, the same rule ADR 0014 sets for upstream skills.

## Considered options

- **A Homebrew tap.** Homebrew would handle the download, `PATH`, and uninstall. `brew upgrade` deletes the old version's files at once, while a running session may still read its flows from them, and it doesn't restart services. It would also make Homebrew a requirement.
- **An npm package.** Every Mac would need Node, which ADR 0003 requires only for repos with a web app.
- **Plugin first.** `claude plugin install` would come first, then a skill would copy the runner to a stable path. Every flow would exist twice, once in the plugin cache and once in the runner's copy, and the two could drift apart. The plugin cache path also changes on every update.
- **Automatic updates,** the way Claude Code updates itself. Fixes would arrive sooner, but a version nobody chose would change what every running factory does.

## Consequences

- v1 runs on Apple Silicon only. Bun's arm64 binary is ad-hoc signed and runs, but a cross-compiled Intel binary carries a broken signature. Files that `curl` downloads get no quarantine flag, so the binary needs no notarization. An ad-hoc signature gives each build a new identity, so a macOS privacy grant to the runner doesn't survive an update. ADR 0007 drops the setting that triggered one, and its watchdog catches a session that another prompt blocks.
- The runner checks GitHub Releases once a day, and `flight-deck status` shows when a newer version exists. `flight-deck update [<version>]` downloads the version, checks its SHA-256, unpacks it, and switches `current`. The runner then drains: it starts no new session, lets running ones finish in their own version folder, and restarts on the new version. Naming an older version rolls back. The runner keeps the current version, the previous one, and any version a session still uses.
- Each outbox names the version that wrote it, and `flight-deck apply` refuses an outbox from another version and names that version.
- The repo record carries `schema = <n>`. A version that changes the schema ships a migration that gives each new field the value that keeps the old behavior, such as a threshold of 0 for a new signal. Migrations chain, so a repo can skip versions. The runner migrates the record each time it reads it, so an update neither pauses work nor changes behavior. Rerunning setup writes the migrated record (ADR 0017). A record whose `schema` is newer than the runner's pauses the issue and asks for `flight-deck update`. `flight-deck status` lists each repo whose record is behind.
- The hand-run skills are a user-scope plugin installed from a local-folder marketplace at `~/.local/share/flight-deck/current/plugin`. Its skills are `flight-setup`, `flight-new`, `flight-issue`, `flight-plan`, `flight-build`, `flight-check`, and `flight-debrief`. Each sets `disable-model-invocation: true`, and the plugin ships no hooks, MCP servers, or agents, so it adds only `/` menu entries in a repo without a factory. Claude Code follows the `current` link each time a session loads the plugin, so an update reaches the maintainer's own sessions without a plugin command. The skills the maintainer runs in their own agent, and any flow run by hand, read their bundled skills through the same link. Factory sessions get `--plugin-dir` with the exact version folder instead.
- `flight-deck install` skips any step that's already done, so a failed install reruns from the top. It never installs another tool. Its steps, in order:
	1. Check for Claude Code at the version's minimum, git, and `gh` 2.99.0 or later (ADR 0009). If one is missing or too old, print the fix, such as `brew upgrade gh`, and stop.
	2. Ask whether sessions use the subscription or an API key (ADR 0005). For an API key, read the key at a hidden prompt and write it to `credentials.env`.
	3. Set up the machine user. Open GitHub's signup page, then the classic-token page preset to the `repo` and `read:org` scopes and a one-year expiry. Sign the token in with `flight-deck login github` (ADR 0005).
	4. Write `~/.config/flight-deck/config.toml` with an empty repo list and the defaults for the concurrency cap, the usage thresholds, and each stage's model. It also holds the absolute paths of `claude`, `git`, and `gh`, because a LaunchAgent's `PATH` is only `/usr/bin:/bin:/usr/sbin:/sbin`.
	5. Register the hand-run plugin with `claude plugin marketplace add` and `claude plugin install <plugin>@<marketplace>`.
	6. Write the launchers and both LaunchAgents (ADR 0024), load them, and wait for the runner's first poll.
	7. Ask the runner for a trial run and one test notification.
	8. Tell the maintainer to run `/flight-setup` in a repo.
- The maintainer types every secret into the `flight-deck` CLI, never into a Claude session, so no transcript holds one. Each `flight-deck login` command also runs alone, so the trouble issue for an expired token can name it (ADR 0011).
- Each Flight Deck version names the oldest Claude Code version it was tested on. Install checks it, and so does the runner before every session. Below it, the runner reports trouble (ADR 0011) and starts nothing. No version sets a maximum, which would stop every factory at each Claude Code update. Each transcript records its Claude Code version, so debrief can tie a run of failures to an update.
- `flight-deck update --from <folder>` installs a local build, for building Flight Deck itself and for dry runs.
- The data folder, `~/.local/share/flight-deck/`, also holds the launchers (ADR 0024), the runner's session list and log, and `repos/<owner>/<repo>/` for each registered repo. Each repo's folder holds Flight Deck's clone, the transcripts, the signal counts, and the filed proposals. `~/.config/flight-deck/` holds `config.toml`, `credentials.env`, and the machine user's `gh/` folder.
- `flight-deck uninstall` refuses while a session runs and names `flight-deck stop`. After it unregisters every repo (ADR 0017), it removes both agents and their launchers (ADR 0024), the hand-run plugin and its marketplace entry, the version folders, and the `~/.local/bin/flight-deck` link. It asks separately before it deletes the data folder and `~/.config/flight-deck/`. Last, it lists what stays outside the Mac: each repo's record and factory statuses, each workspace's Flight Deck app, and the machine user and its token. It links to the pages that delete each app and revoke the token.
