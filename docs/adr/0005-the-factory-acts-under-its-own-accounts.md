# The factory acts under its own accounts

Unattended factory work never runs under the maintainer's accounts. In GitHub, the factory is a machine user: a second account the maintainer creates once and invites to each repo with a factory, with the Write role and a classic token scoped to `repo` and `read:org`. On an org repo, the machine user is an outside collaborator, not an organization member. In Linear, the factory is an app user: an OAuth app named Flight Deck that the maintainer creates in each workspace with `actor=app`, whose tokens the runner mints with the client-credentials grant. The app has only the `read` and `write` scopes and no webhook. Sessions read Linear through a second app, Flight Deck Reader, which has only the `read` scope. It is a credential, not an account the factory acts under, because nothing in Linear ever appears under its name. With its own accounts, the factory can't approve or merge its own PR once a ruleset requires one approval, as long as no CI job a factory branch starts can approve a PR (ADR 0025). Its PRs also show that an agent wrote them, without an attribution line. A flow the maintainer runs by hand acts as the maintainer, because the maintainer watched it.

## Considered options

- **The maintainer's accounts.** Setup would need no second account. A PR author can't approve their own PR, and the maintainer's account can bypass every ruleset, so nothing at GitHub would stop an unattended merge. Linear skips view-subscription notifications for a user's own actions, and every factory comment would read as the maintainer's. The factory would also hold the maintainer's admin rights on every repo they own.
- **A GitHub App.** It is the usual identity for automation, with short-lived tokens and a `name[bot]` author. `gh --attach` rejects App installation tokens, and the `gh` maintainers call that intended, so build couldn't upload screenshots to the PR. On private repos, CodeRabbit never seats an App on its own, and Copilot bills a bot's PR only to an organization on Copilot Business or Enterprise.
- **One Linear app for the runner and the sessions.** Sessions would mint `read` tokens and the runner `read write` tokens from the same app. Linear holds up to 1,000 client-credentials tokens per app only while they share the same scopes. A request with other scopes revokes every existing token and replaces it with the new one. Each session's connection would revoke the runner's token, and the runner's next mint would revoke every live session's.
- **One app, with `read write` for sessions too.** Only the session's list of allowed MCP tools would keep a session from writing, against ADR 0007's rule that no session holds a write credential.
- **A local proxy for the Linear MCP server.** Sessions would connect to the runner, which would pass on only the read tools under its own token. It needs one app and one token, but Flight Deck's own code would be the only thing between a session and a write.
- **One shared Flight Deck app in Linear.** Every maintainer would authorize one app instead of creating their own. Other workspaces can install it only after Linear's integration directory lists it, and the directory says it generally doesn't accept apps built by hobbyists. If its owner removed it, every factory would lose its Linear identity at once.

## Consequences

- A private repo needs GitHub Pro or Team, because GitHub Free enforces rulesets on public repos only. Setup adds a factory only where a ruleset can require one approval. The maintainer stays on the bypass list.
- The machine user may need its own review-bot plan or seat, on a public repo as well as a private one (ADR 0010). Flight Deck never requires one (ADR 0016).
- The machine user's token is a classic one, because a fine-grained token can't reach a repo where its owner is only a collaborator. The token expires after one year. The `repo` scope reaches only the repos the machine user is invited to. `gh auth login` rejects a token without `read:org`, which only reads organization membership and teams. The token has no `workflow` scope on purpose, so the factory can't push an added or edited workflow file that no other branch holds, and a planted instruction can't rewrite what CI hands a factory branch (ADR 0025). The Write role also lets the token create, update, and delete the repo's secrets, though not read them. Only the runner holds the token (ADR 0007).
- `flight-deck login github` signs the token in to `gh` in Flight Deck's own config folder, `~/.config/flight-deck/gh`, and refuses a token that belongs to the maintainer's account. The runner runs `gh` with `GH_CONFIG_DIR` set to that folder. A second Mac signs in the same machine user with a token of its own and reuses each workspace's two Linear apps.
- An `actor=app` app can't hold the admin scope. Setup creates statuses and changes team settings with the maintainer's personal Linear key (ADR 0017).
- A Linear client-credentials token lasts 30 days, has no refresh token, and lives only in the runner's memory. Flight Deck never saves one. Each app may hold 1,000 active tokens, and Linear's docs don't say what happens to a request past that.
- The runner mints one Flight Deck Reader token as it starts each session. The session's `headersHelper` runs a `flight-deck` subcommand that asks the runner for that token and mints nothing itself (ADR 0007). Claude Code reruns the helper after a 401 or 403, and the runner then mints a replacement and revokes the old token. When the session exits, is stopped, or is killed, the runner revokes its token with `POST https://api.linear.app/oauth/revoke`. Active Reader tokens stay at the number of sessions running, plus any a crashed runner left behind until they expire.
- The runner mints its own Flight Deck token at start and after a 401, and revokes it on every clean shutdown: a drain, an update, and `flight-deck stop`.
- When the runner can't mint a token, it holds new work (ADR 0021), shows the failure in the menu bar app and in `flight-deck status`, posts ADR 0011's macOS notification, and retries with backoff. A full token pool, a rotated client secret, a deleted app, and a Linear outage all look the same from the Mac. Once a mint works, the runner files a trouble issue (ADR 0011) that says what failed and for how long.
- An extra MCP server, such as Figma's, may use the maintainer's own sign-in. Factory accounts are required only where the factory writes under its own name, in Linear and GitHub.
- Flight Deck never reads, stores, or passes on the maintainer's Claude login. Anthropic's terms bar third-party developers from collecting, storing, or intermediating Claude.ai credentials, so each session's `claude` binary reads the login itself. Every other tool keeps its own sign-in where it can, and the rest goes in `~/.config/flight-deck/credentials.env` with mode `0600`. The file holds the client ID and secret of both Linear apps and the maintainer's personal Linear key for each workspace, any Claude API key, and the keys of MCP servers that take only an API key. The runner refuses to start if anyone else can read the file, and a session gets only the variables it needs.
- Sessions use the maintainer's Claude subscription by default, or an API key that the maintainer picks at install. On the subscription, the runner strips `ANTHROPIC_API_KEY` from each session's environment, because a stray key moves billing to the API. On an API key, `--settings` points `apiKeyHelper` at a `flight-deck` subcommand that prints the key from `credentials.env`. The subscription needs Claude Pro or above.
- The runner files a trouble issue (ADR 0011) when the machine user's token expires or is revoked, when Claude Code warns that its login expires soon, or when a session fails with `Login expired`. The issue names the command that signs in again, such as `flight-deck login github`.
