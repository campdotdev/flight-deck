# The maintainer watches the runner from a menu bar app

Flags reach the maintainer through Linear (ADR 0011), but nothing showed the runner itself: what it's running, whether it's alive, and how much of the plan it has used. After the FlutedGlass dry run, the maintainer asked for one place to see that. A prototype over that run's state tried four forms, and the maintainer chose a menu bar app that shows the bare minimum. Flight Deck ships one for the Mac's runner. Its icon shows how many issues need the maintainer, and whether the runner is working, held, stopped, or not responding. Its menu lists, in this order, the flagged issue that has waited longest, the running sessions and runner jobs, the plan usage, the controls **Start**, **Hold new work**, and **Stop**, and **Open Linear**. The app reads the runner's state and calls the runner's own commands, so it holds no credential and writes nothing to Linear or GitHub. It doesn't answer a pause, send an issue, or queue a job.

## Considered options

- **A local web page that leads with what needs the maintainer.** It had room for the spec's numbers: sessions, session time, cost at API prices, and the time spent waiting on the maintainer. The maintainer wants to think a fuller UI through before v1 commits to one.
- **A board and timeline page.** It showed where every issue sits and when each session ran. That suits a look back at a run, not a glance.
- **A richer `flight-deck status` on its own.** It shows the same content, but only in an open terminal.
- **Up to 5 flags, with debrief's proposals on a row of their own.** The prototype showed this first. The maintainer cut it to one flag and one row into Linear.
- **A carousel of flags.** A macOS menu has no carousel, and paging through flags in the menu would repeat the Needs you view.
- **Answering a pause from the menu.** The runner holds only the Flight Deck app's Linear key, so an answer would read as Flight Deck's, not the maintainer's. Linear already takes the one-word answer from the phone (ADR 0019). Each flagged issue in the menu opens in Linear instead.

## Consequences

- The menu shows one flagged issue: the longest-waiting one that holds up work. Debrief's proposals hold up nothing, so the menu shows the oldest proposal only when no other flag waits. When the shown flag clears, the next one takes its place. Below it, a row such as "10 more in Linear" opens the Needs you view, which lists the rest. The icon counts every flag.
- The menu's header shows the runner's state and how long ago it last polled Linear, such as "Working · polled Linear 0s ago". The flag's row shows its status line (ADR 0019), the repo, the issue's title, and how long the flag has waited. A click opens the issue in Linear. The Running section lists each session's stage, repo, and issue, with its time against the stage's time limit, and each runner job, such as a wait for CI or a review bot. Its heading counts sessions against the concurrency cap, such as "Running · 0 of 2 sessions".
- Needs you is one shared view for the whole workspace, so a single link covers every factory in it. It lists the issues assigned to the maintainer that are in flight or that the Flight Deck app filed, grouped by status. Changes ready for review, paused issues, and the proposals and trouble issues in Triage each get their own group. Linear leaves Triage out of a view unless its filter names Triage, so the filter does. The filter also names each factory team's In Review, where a change ready for review waits. Linear's filters can't see where an issue came from or who opened its PR, so the view also lists the maintainer's own issues in In Review that are assigned to them, such as by Linear's self-assignment preference. On a solo team, those PRs wait on the maintainer too. The icon reads the runner's own flags, so its count leaves them out. My Issues would also list the maintainer's own work in other teams.
- ADR 0011 turned down subscribing to a "Needs you" view, because a filter on status would notify the maintainer before the bot round settles. This view filters on the assignment, which the runner makes only when a flag is real, and nobody subscribes to it. Notifications still come from the assignment.
- Setup creates the Needs you view with the first factory in a workspace, under the maintainer's login, and adds each later factory's statuses to its filter. `flight-deck remove` takes a factory's statuses out of it and deletes the view with the workspace's last factory (ADR 0017).
- A hold stops the runner from starting new sessions while running sessions and jobs finish. A held runner still polls, applies outboxes, lands issues, and flags the maintainer. A trial run, which takes no issue, still starts under most holds, and a held runner starts no new cache refresh. Stop also kills a running refresh. **Hold new work** puts the runner on hold, and **Start** ends the hold. They run `flight-deck hold` and `flight-deck start`, and **Stop** runs `flight-deck stop`, which holds the runner before it ends every session (ADR 0007).
- The runner also holds itself short of the plan limits (ADR 0002). That hold ends on its own when the limit resets, and the menu shows when.
- **Stop** asks the maintainer to confirm while a session runs. Each stopped session's issue pauses without a flag (ADR 0011) and stays paused until the maintainer moves it or answers `retry` (ADR 0019).
- Usage shows the plan's five-hour window and its week, each with its reset time. On an API key, it shows spending against the daily and monthly caps (ADR 0007).
- One runner serves every repo on the Mac (ADR 0002), so the menu covers every factory on it and names each issue's repo. **Open Linear** opens the Needs you view.
- Each Linear workspace has its own Needs you view, so when the Mac's factories span two workspaces, the menu gets one "N more in <workspace>" row and one **Open Linear** item for each. With one workspace, the menu is as above. When the Flight Deck app can't read the view, both open the maintainer's My Issues page, which lists every flag but also the maintainer's own work. Reading the view with the setup key would give the runner a second Linear identity (ADR 0005).
- The menu and `flight-deck status` read the same state, which the runner rewrites at each poll, so they always agree. Both lag Linear by up to one poll, about a minute.
- `flight-deck status` prints that state as text, for every factory on the Mac:
	- The runner's state and when it last polled.
	- Each running session, with its stage and its time against the stage's time limit.
	- Usage against the thresholds or caps where the runner holds itself, with the reset times.
	- Open trouble causes and stale takes (ADR 0011).
	- Debrief's signal counts (ADR 0012).
- When the runner's heartbeat is more than 3 minutes old, the icon says the runner isn't responding. Silence no longer hides a dead runner, though a closed lid still stops the factory.
- A hold scoped to one workspace or one repo, such as a failed Linear token mint, leaves the runner working for the other factories. When such holds cover every registered repo, nothing can start, so the icon and the header show the runner as held and name the cause. A trouble cause the runner can't file as an issue shows as a row under the flag, so it stays visible after its notification goes. It isn't a flag, so the icon doesn't count it.
- The menu posts no notifications. Flags reach the maintainer through Linear, and the runner posts a macOS notification only for trouble that stops it (ADR 0011).
- v1 has no fuller local UI: no board, no timeline, no spec numbers, and no local PR walkthrough. ADR 0020 already ruled out a published walkthrough. A fuller UI is a later effort.
- ADR 0024 decides how the app is built, shipped, and started, and where it first appears in the menu bar.
