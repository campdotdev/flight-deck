# Intake lands unsent issues in Triage and runs no session before the send

On the board, a triage routine ran twice a day. It checked new issues for duplicates and past rejections, reproduced bugs, and accepted up to 5 a day into Todo. Later decisions took those jobs away. The maintainer's send is the only gate (ADR 0006), and plan runs the duplicate and already-built checks after the send. So intake runs no session, and plan is the first session the runner starts for an issue. Setup turns on the team's Triage, and every issue the maintainer didn't file lands there: GitHub issues, Sentry and PostHog errors, default-branch failures, follow-up issues, proposals, and the runner's trouble issues. The maintainer empties Triage by sending an issue, moving it to Backlog, canceling it, marking it a duplicate, or moving a proposal they handled by hand to Done (ADR 0012). GitHub issues arrive through Linear's one-way GitHub Issues Sync. The runner files default-branch failures itself, by polling GitHub.

## Considered options

- **The board's triage routine.** An unattended session would read a stranger's text before the maintainer has seen it. It would spend plan limits on issues nobody sends, and it would repeat plan's checks.
- **Triage off, with every issue in Backlog.** GitHub issues, error reports, and the factory's issues would mix with the maintainer's own backlog. The "Filed by Flight Deck" view would separate only the factory's issues.
- **Two-way GitHub sync.** Every issue created in the team would become a GitHub issue, and Linear has no setting that keeps one issue from syncing. On a public repo, follow-up issues, trouble issues, and proposals that quote session transcripts would be public.
- **The runner polls GitHub issues instead of Linear's sync.** No issue would ever need ADR 0008's detach. The poll would be more runner code, and it would stop while the Mac sleeps. Linear's sync runs between the two clouds.
- **A GitHub Actions workflow or a webhook for default-branch failures.** A workflow puts a Flight Deck file and a Linear key in the repo, against ADR 0003. A webhook needs a public URL.

## Consequences

- Setup asks before it turns on Triage, because any integration the team already has starts filing there too. If the maintainer declines, the same issues land in Backlog. The record's `[tracker.statuses]` map gains an `intake` role for that status. Linear sends an issue created through the API or the MCP server to the team's default status unless the call names one, even with Triage on. So the runner names the status, and so does every flow that files an issue.
- Issues the maintainer files skip Triage. `/flight-issue` and `/flight-new` land their issues in Backlog, unless the maintainer sends them at once. Setup files in Backlog each gap issue the maintainer accepts, and sending one stays a separate step. A spec starts in Backlog and its sub-issues in Ready to plan, so sending the spec sends them. When the maintainer sends a spec, the runner checks its shape in code before it cuts the spec branch. The spec needs at least one open sub-issue, no parent of its own, every sub-issue in the same team and in Ready to plan or a closed status, no sub-issue with sub-issues of its own, no blocking cycle, and no blocking relation between the spec and its own sub-issues. So a spec never nests, and never waits on itself. A spec that fails pauses with the reason.
- `/flight-issue` files one issue in the repo's team under the maintainer's Linear login, through the Linear MCP server, because it isn't a stage and writes no outbox. It writes a report, never a brief: what's wrong or wanted, where, and how to see it. When the issue renames or removes something a release may have shipped, it asks whether the old form keeps working and writes the answer in a `## Breaks` section, one line per break: the old name, the new one, and "old name removed" or "old name kept as an alias". Plan reads that section as the maintainer accepting each removal, and decides against the last release whether the name ever shipped (ADR 0026). Then `/flight-issue` asks whether to send the issue.
- `/flight-new` takes any context: a sentence, a doc, a design link, or an existing issue. Before its first question, it searches the tracker for words inside descriptions, which a `list_issues` query misses, and follows any decision record the code points to. It grills only on what the context leaves open. Unless a design link came in, it asks whether the work needs a design, and a "no" writes a `## Design` section that says why none is needed. It asks about each rename or removal and writes a `## Breaks` section the way `/flight-issue` does. If the change fits one build by plan's size rule (ADR 0026), it files one issue the way `/flight-issue` does. Otherwise it writes the spec and its sub-issues, and files work the spec's change doesn't need as an independent issue (ADR 0004).
- Given an existing issue, such as one plan paused as too big, `/flight-new` writes the spec into it, keeps the report in a fold, and starts from plan's proposed split. It detaches a synced issue first (ADR 0008). No session sees the maintainer's checkout, so `/flight-new` lists the files it changed, such as `GLOSSARY.md` and the ADRs, and tells the maintainer to commit them to the default branch. Last, it asks whether to send.
- An arrival in Triage flags nothing. Proposals and trouble issues are still flagged, under ADRs 0011 and 0012. No label marks an issue that needs more information before the send. Asking a reporter for more is the maintainer's job, on GitHub.
- Setup won't add a factory to a team that syncs two-way, and it walks the maintainer through switching the team to one-way by hand. It reads the sync mode from the `bidirectional` flag on the team's GitHub sync mapping. It also refuses a team whose sync maps another GitHub repo, because a sent issue from that repo would be built in this one. On a team with no sync, setup asks whether GitHub issues should reach Linear. Each walkthrough names the repos and permissions that Linear's GitHub app gets. One-way sync never creates a GitHub issue from Linear. It still syncs comments in the synced thread, and open or closed status, in both directions, so ADR 0008's detach still applies. A detached issue stops receiving the reporter's comments, so the runner fetches the linked GitHub issue's body and comments into each plan and build session's inbox. Check and the bot round don't get them, because check reads from GitHub only what ADR 0028 lists, and no stranger's later GitHub text reaches the session that judges.
- On Shaders, a GitHub issue reached Triage within seconds. Linear names the GitHub integration as its creator and records no Linear user. Until the detach, GitHub's state moves the Linear issue: a close as not planned moves it to Canceled, a close as completed moves it to Done, and a reopen moves it back to Triage.
- Sentry and PostHog work only with a public team. Flight Deck writes no code for them. Setup finds their SDK in the repo and walks the maintainer through connecting them. Setup can't read either service, so these two hand steps are the ones it can't check, and the maintainer confirms each by saying it's done. Like adding a one-way sync to a team with none, they come after `setup apply`, because they start issues flowing into the team (ADR 0017). In Sentry, the maintainer adds an issue alert rule with the triggers "A new issue is created" and "A resolved issue regresses", and the Linear integration as its action. In PostHog, the maintainer adds an error-tracking alert on "Issue created" with Linear as its destination. PostHog has no Linear destination for reopened or spiking issues, so those don't reach intake in v1. PostHog's destination names no status, so its issues may land in the team's default status instead.
- The tracker interface says which sources a tracker receives natively: GitHub issues, Sentry, and PostHog. A future tracker that lacks one gets a runner poll for that source. Linear receives all three, so v1 builds no poll for them.
- The runner's poll counts runs on the default branch whose conclusion is `failure`, `timed_out`, or `startup_failure`, every such run of the record's `release_workflows`, and failed deployments to the record's `production_environments`. A `cancelled` run doesn't count. A `success` run passes only when every job that failed since the last pass ran in it and succeeded, because a path filter or an `if:` can skip the job that broke. The poll reads `GET /repos/{owner}/{repo}/actions/runs` filtered by `created`, so it catches up on runs that finished while the Mac slept. It keeps one open issue per workflow or environment. The issue's title is "<workflow> fails on <branch>" or "Deploy to <environment> failed", in plain text, because Linear shows a title as plain text. When two workflows share a name, each title adds its file name. Runs of one workflow count in the order they were created, so an older run that finishes late reports nothing. Its body gives the run link, the head commit and its title, the failed jobs and steps, and the conclusion. A repeat failure adds a comment, at most one per workflow or environment per hour, carrying a count of the runs it covers, because a `*/15` schedule would otherwise post hundreds and each session reads the thread. The next run that passes comments at once. The maintainer chose the hourly limit on 2026-11-08. The runner never closes the issue. The issue holds no log text, because a public team would show it.
- Only a run the default branch itself starts counts: a run from the repo itself, never a fork, even one whose branch has the default branch's name, with the event `push`, `schedule`, `workflow_dispatch`, or `repository_dispatch`. A `workflow_run` run doesn't count, because a stranger's fork PR can start the chain. A run that an issue, a comment, a review, or a pull request starts never counts, whatever its branch, because a stranger can start one. That covers `issue_comment`, `pull_request_target`, and the `dynamic` runs of Copilot code review. A release workflow's run also counts on a `release` event, and on any branch or tag except a factory branch, whose CI check reads.
- The repeat failure's comment opens with "🔴 Failed again", and the next pass's with "🟢 Passed" (ADR 0019). Neither flags or moves the issue. On an issue that isn't in flight, the runner's comments leave the maintainer's subscription alone, because an unsent issue stays the maintainer's (ADR 0011).
- When a failure issue closes as completed, such as Done after its fix merged, the key's next counted run still reports on it. A pass comments there. A failure files a new issue, related to the closed one, whose description says which issue it follows. A canceled or duplicate issue starts fresh.
- A team switched to two-way sync after setup would make every issue the factory files public, and the detach and top-level comments were tested only under one-way sync. So the runner reads the workspace's sync mappings at its start, after each new registration, and hourly. A two-way mapping on a factory's team, or a mapping of another GitHub repo, opens a trouble cause that skips that repo's whole poll, as a missing status does: nothing in the team is moved, flagged, commented on, briefed, or filed. A running session finishes, and its outbox waits unapplied until the cause clears, and `flight-deck apply` refuses meanwhile. Filing would sync the trouble issue too, so the cause only posts a macOS notification (ADR 0011). `/flight-issue` and `/flight-new` file nothing while `flight-deck status` shows the cause. The runner reads the mappings as the Flight Deck app, or with the maintainer's setup key when Linear won't let the app read them (ADR 0005). When neither read works, it keeps the last mode it read, across a restart, and posts one macOS notification after 24 hours with no read.
- A release workflow can run on several refs, so its order and pass tests apply within each ref group: the default branch, each other branch, and all tags together. It still has one open issue.
- A GitHub read that a plan or build session needs, and that fails for 3 hours, pauses the issue with `retry`, the limit ADR 0002 gives a Linear write. The maintainer chose this on 2026-11-08.
- Setup's `ci_fails` gap issue counts as its workflow's open failure issue, because one break gets one issue (ADR 0017). The poll reads setup's record of it before it handles that workflow's next counted run, comments there, and tests a pass against the jobs setup recorded. The link lives in setup's folder, so a lost State file or an `unregister` loses it, and the next failure files a new issue. The maintainer chose this on 2026-11-08.
- A failure poll that stays blind, because a read keeps failing or the default branch's record is invalid, posts one macOS notification after 24 hours and holds a menu row until it clears (ADR 0021). Nothing stops, so it files no trouble issue. The sync read's 24-hour notification gets the same row. The maintainer chose this on 2026-11-08.
- The record's `[intake]` section holds both lists, and setup fills them from the repo's workflows and recent deployments. `release_workflows` names the workflows that publish a package or deploy, whatever starts them, such as a Release workflow on pushes to the default branch, and their runs count whatever their branch. Setup proposes each workflow that runs on a tag or a GitHub release, uses a release action, or reads as publishing or deploying, and the maintainer confirms the list. The maintainer chose this on 2026-11-08, so a failed publish counts under Escaped's release rule (ADR 0012). The runner matches `production_environments` by environment name, never by GitHub's `production_environment` flag, which Vercel sets to false even on production deploys.
- Plan works only an issue's latest failures: the newest failure and the ones before it that no passing run separates from it. The runner fetches the failed jobs' logs for those runs alone into the inbox of each plan and build session that works the issue. An issue nobody closes can collect unrelated failures. A replay of Shaders' runs on `main` since 2026-09-05 filed one CI issue with one cause, and one Release issue that held two causes 19 days apart, separated by a passing run: an npm `ENEEDAUTH` on 09-08, and a push the merge queue rejected on 09-27.
- Before plan, build, or check files a follow-up issue for a command that fails on the default branch, it looks for an open default-branch failure. If it finds one, it names that issue in its handoff and files nothing.
- Security alerts, such as Dependabot and code scanning, and pull requests the factory didn't open don't reach intake in v1.
