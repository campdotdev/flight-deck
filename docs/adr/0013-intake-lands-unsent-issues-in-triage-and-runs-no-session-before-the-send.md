# Intake lands unsent issues in Triage and runs no session before the send

On the board, a triage routine ran twice a day. It checked new issues for duplicates and past rejections, reproduced bugs, and accepted up to 5 a day into Todo. Later decisions took those jobs away. The maintainer's send is the only gate (ADR 0006), and plan runs the duplicate and already-built checks after the send. So intake runs no session, and plan is the first session to read an issue. Setup turns on the team's Triage, and every issue the maintainer didn't file lands there: GitHub issues, Sentry and PostHog errors, default-branch failures, follow-up issues, proposals, and the runner's trouble issues. The maintainer empties Triage by sending an issue, moving it to Backlog, canceling it, or marking it a duplicate. GitHub issues arrive through Linear's one-way GitHub Issues Sync. The runner files default-branch failures itself, by polling GitHub.

## Considered options

- **The board's triage routine.** An unattended session would read a stranger's text before the maintainer has seen it. It would spend plan limits on issues nobody sends, and it would repeat plan's checks.
- **Triage off, with every issue in Backlog.** GitHub issues, error reports, and the factory's issues would mix with the maintainer's own backlog. The "Filed by Flight Deck" view would separate only the factory's issues.
- **Two-way GitHub sync.** Every issue created in the team would become a GitHub issue, and Linear has no setting that keeps one issue from syncing. On a public repo, follow-up issues, trouble issues, and proposals that quote session transcripts would be public.
- **The runner polls GitHub issues instead of Linear's sync.** No issue would ever need ADR 0008's detach. The poll would be more runner code, and it would stop while the Mac sleeps. Linear's sync runs between the two clouds.
- **A GitHub Actions workflow or a webhook for default-branch failures.** A workflow puts a Flight Deck file and a Linear key in the repo, against ADR 0003. A webhook needs a public URL.

## Consequences

- Setup asks before it turns on Triage, because any integration the team already has starts filing there too. If the maintainer declines, the same issues land in Backlog. The record's `[tracker.statuses]` map gains an `intake` role for that status. Linear sends an issue created through the API to the team's default status unless the call names one, so the runner names it.
- Issues the maintainer files skip Triage. `/flight-issue`, `/flight-new`, and setup's gap issues land in Backlog, unless the maintainer sends them at once. A spec starts in Backlog and its sub-issues in Ready to plan, so sending the spec sends them. When the maintainer sends a spec, the runner checks its shape in code before it cuts the spec branch, and it pauses a spec that fails.
- An arrival in Triage flags nothing. Proposals and trouble issues are still flagged, under ADRs 0011 and 0012. No label marks an issue that needs more information before the send. Asking a reporter for more is the maintainer's job, on GitHub.
- Setup won't add a factory to a team that syncs two-way, and it offers to switch the team to one-way. One-way sync never creates a GitHub issue from Linear. It still syncs comments in the synced thread, and open or closed status, in both directions, so ADR 0008's detach still applies. A detached issue stops receiving the reporter's comments, so the runner fetches the linked GitHub issue's body and comments into each session's inbox.
- Sentry and PostHog work only with a public team. Flight Deck writes no code for them. Setup finds their SDK in the repo and walks the maintainer through connecting them.
- The tracker interface says which sources a tracker receives natively: GitHub issues, Sentry, and PostHog. A future tracker that lacks one gets a runner poll for that source. Linear receives all three, so v1 builds no poll for them.
- The runner's poll counts runs on the default branch that failed, timed out, or failed to start, every run of the record's `release_workflows`, and failed deployments to the record's `production_environments`. It keeps one open issue per workflow or environment. A repeat failure adds a comment, and so does the next run that passes. The runner never closes the issue. The issue holds no log text, because a public team would show it. The runner fetches the failed jobs' logs into the inbox of each session that works the issue.
- Before build or check files a follow-up issue for a command that fails on the default branch, it looks for an open default-branch failure. If it finds one, it names that issue in its handoff and files nothing.
- Security alerts, such as Dependabot and code scanning, and pull requests the factory didn't open don't reach intake in v1.
