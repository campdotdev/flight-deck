# Factory sessions write only to their worktree and outbox

A factory session runs as the maintainer's macOS user, so it can reach the maintainer's own credentials. Sandboxed Bash read a Keychain item in a test, and the maintainer is on the ruleset's bypass list. A session that ran `git push origin main` with the maintainer's git login would get past the one approval that ADR 0005 made the hard stop. So no session holds a write credential. A session commits in its worktree and leaves an outbox: its handoff, its status move, and any PR body, media, or verdict. When the session exits, the runner checks the outbox against the stage's rules and makes every write in Linear and GitHub itself. Sessions get the Linear MCP server's read tools only and can't reach GitHub's hosts. Before check starts, the runner fetches what check needs from GitHub into the worktree. The runner never runs the repo's code outside a sandbox with a session's limits. These limits defend against mistakes and against instructions planted in text the factory reads, such as a stranger's comment on a public PR. They don't defend against code that escapes macOS's sandbox, and they don't apply to a flow the maintainer runs by hand. They also stop at the Mac. What the repo's CI hands a factory branch is ADR 0025's rule.

## Considered options

- **Sessions write to Linear through the MCP server, behind a hook.** A `PreToolUse` hook would check each `save_issue` and `save_comment` call against the stage's allowed moves, and the runner would still make the GitHub writes. A session that died halfway would leave a handoff half posted.
- **Sessions hold the machine user's token,** as earlier tickets assumed, behind deny rules, hooks, and rulesets. Deny rules match command text, so `Bash(git push *)` doesn't stop `git -C . push`. A session could also skip the machine user and ask `git credential-osxkeychain` for the maintainer's token.
- **The sandbox runtime (`srt`) around the whole `claude` process.** It confines file tools, hooks, and MCP servers too, and the subscription login worked inside it in a test. It is a beta research preview at v0.0.80. It doesn't handle a worktree whose git folder lives elsewhere, and Claude Code's own Bash sandbox can't start inside it. It can replace the built-in sandbox later without changing anything else here.
- **Sessions run as a second macOS user** with its own Keychain. That closes the Keychain gap. It needs admin rights, a second Claude login, and repos that both users can read.

## Consequences

- The runner pushes fast-forward only, through `gh`'s credential helper, so git uses the machine user's `gh` login. Build is the only session whose commits it pushes, so check never pushes. When build works on the spec issue itself, the runner pushes build's commits straight to the spec branch. A sub-issue's commits reach the spec branch only through the runner's own landings, which push too (ADR 0004). The one force push is the answer `reset`, which puts the runner's own commit back on a factory branch or spec branch that holds a commit the runner didn't push. Before every push, the runner reruns ADR 0025's CI audit, and a diff that changes a file under `.github/workflows/` pauses the issue before the push (ADR 0025). The runner also opens and edits the PR, attaches media, sets `flight-deck/check`, marks the PR ready, posts comments, and moves statuses. Build and check decide those writes (ADRs 0027 and 0028). Only build's outbox can carry a PR body, and only check's can carry a verdict.
- A stage's outbox can also list follow-up issues. The runner files each one in the record's `intake` status (ADR 0013) and links it to the issue as related.
- The runner's own code enforces the lifecycle from ADR 0006. A stage moves its issue from its working status to its handoff status or to Paused. Plan may also mark its issue a duplicate of an open issue. Only the runner closes issues, in the three cases ADR 0006 lists. The runner also moves an issue from In Review to Ready to build, with a comment, when its PR starts to conflict with the default branch.
- A flow the maintainer runs by hand writes the same outbox and applies it with `flight-deck apply`, under the maintainer's own logins: their `gh` login and the personal Linear key that setup uses (ADR 0017). The runner and hand runs share one write path.
- Every factory session runs in `dontAsk` with Claude Code's Bash sandbox on. `--settings` sets `allowUnsandboxedCommands: false` and `failIfUnavailable: true`, which makes the sandbox admin-required, so a repo's settings can't turn it off or loosen it.
- Sandboxed commands can't read under `~` except Flight Deck's clone and the paths the repo record reopens, such as `~/.nvm`. `--settings` puts `~/` in `sandbox.filesystem.denyRead` and each reopened path in `allowRead`. Sandboxed commands reach only the hosts the record lists, through `sandbox.network.allowedDomains`. `github.com`, `api.github.com`, and `uploads.github.com` are always in `deniedDomains`, which beats any allowed wildcard and blocks git over SSH too. WebFetch runs outside the sandbox, so it gets the same host list plus documentation sites. Each extra MCP server exposes only the tools the record lists for it. Setup proposes only a server's read tools, and a write tool goes on the list only when the maintainer adds it, because the server acts under the maintainer's sign-in (ADR 0005).
- Worktrees, dependency folders, and session temp folders live outside `~`, in a folder only the maintainer's user can open. A read under `~` fails with `EPERM`, not `ENOENT`, and many tools stop on `EPERM` when they look for a file in each folder above the working directory. With worktrees under `~`, Shaders' docs build failed when browserslist read `~/package.json`, and Next and webpack failed on `~/pnpm-lock.yaml` and `~/node_modules`.
- Before a session starts, the runner writes the session's inbox into the session's folder, beside its outbox and outside its worktree. The inbox holds what the stage needs from GitHub, which no session can reach, and what earlier sessions left, such as build's latest claims (ADR 0019). ADR 0028 lists what check's inbox holds. The session reads the inbox as untrusted text and can't write to it. The inbox sits outside the worktree so that the repo's own commands can't read it. In the FlutedGlass dry run, the inbox sat in the worktree, and the spec check's `pnpm format:check` read `.flight-deck/inbox/ci.json` even with an entry in git's `info/exclude`.
- A trial denial under `~` doesn't mean setup reopens the path. turbo reads the Vercel CLI's login file, and reopening it would hand every session a credential. The runner points such a tool at an empty folder through the tool's own variable instead, such as `TURBO_CONFIG_DIR_PATH` and `VERCEL_CONFIG_DIR_PATH`. The repo record has no field for these variables, so each one is runner code.
- MCP servers run outside the sandbox. For a repo with a web app, the browser MCP server is the one process a session drives that can load pages, and a proxy contains it instead of the sandbox (ADR 0009). Chromium can't start from sandboxed Bash on macOS, so a repo's own browser tests run only in CI until the sandbox can start a browser.
- Sessions load the repo's `CLAUDE.md`, skills, and subagents, and nothing that runs code. The runner passes `--setting-sources project`, `disableAllHooks: true`, and `--strict-mcp-config`, and it turns off auto memory and the claude.ai connectors with `autoMemoryEnabled: false` and `disableClaudeAiConnectors: true`. Under `--strict-mcp-config`, only servers passed through `--mcp-config` load, so the runner passes the Linear MCP server and every other server that way. A repo's `env` block outranks the process environment, so the runner sets every variable it depends on in the `env` block of `--settings`. That includes `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, because a repo `env` block that sets it to `0` turns auto memory back on over the settings key. This replaces ADR 0002's `project,local`, because in a worktree `local` loaded the maintainer's own approvals from the main checkout.
- `--setting-sources project` still loads `~/.claude/CLAUDE.md`, and `claudeMdExcludes` ignores a pattern that starts with `~`. So `--settings` excludes, by absolute path, `~/.claude/CLAUDE.md`, `~/.claude/rules/`, and every `CLAUDE.md`, `CLAUDE.local.md`, `.claude/CLAUDE.md`, and `.claude/rules/` in a folder above the worktree.
- Claude Code builds each session's shell snapshot by running the maintainer's shell startup file outside the sandbox, and it ignores `ZDOTDIR`. The runner sets `CLAUDE_CODE_SHELL=/bin/bash`, so a session gets `~/.bashrc`, which most Macs leave nearly empty, instead of `~/.zshrc`. Setup warns when `~/.bashrc` defines aliases or functions.
- The file tools ignore the sandbox, and a bare `Read` allow rule let a session read `~/.zshrc`. So allow rules for the file tools name only the worktree and the outbox, as `Read(//<path>/**)` and `Edit(//<path>/**)`, and `dontAsk` denies every other read. Three more folders get a `Read` rule and no `Edit` rule, and the sandbox reopens each for reads. The first is the session's inbox. The second is the installed version's skills, which flows read as files (ADR 0014). The third is the session's own folder under `~/.claude/projects/`, where Claude Code saves an MCP result too large to return inline and hands the session its path. A Figma page outline on Shaders ran to 358,475 characters, and without that rule `design-check` couldn't search it. The runner doesn't set `blockReadsOutsideWorkingDirectories`. On a Mac with a network mount under `~`, such as OrbStack's, that setting made macOS ask for Network Volumes access on the runner's behalf, and the session blocked until someone answered.
- `--settings` allows `Bash`. Without that rule, `dontAsk` denied sandboxed commands that used `$(...)`, a redirect, or an environment prefix. The sandbox is admin-required, so every command still runs sandboxed.
- `--settings` also allows `Agent`, and `Task` as older builds name it, so a flow can start its reviewer subagents under the session's rules and sandbox. It allows each of the Linear MCP server's read tools by name, the tools the record lists for each extra MCP server, `WebSearch`, and `WebFetch` for the listed hosts, and `dontAsk` denies every other tool. A rule for the whole Linear server, such as `mcp__linear__*`, would also allow `merge_diff`, which can merge a GitHub PR through Linear Diffs. Each session's Linear token also comes from the Flight Deck Reader app, which has only the `read` scope, and the runner revokes it when the session ends (ADR 0005).
- `--settings` sets `attribution` to empty `commit` and `pr` strings and `includeCoAuthoredBy` to `false`, so Claude Code adds no `Co-Authored-By` trailer or PR line of its own, and the repo's rules decide what a commit says. On Shaders, the default trailer broke the repo's rule against agent attribution.
- Git exits when it can't read `~/.gitconfig`. The `env` block sets `GIT_CONFIG_GLOBAL` to Flight Deck's own git config, which sets the commit identity to the machine user's name and GitHub noreply email, and sets `GIT_CONFIG_NOSYSTEM=1`.
- The `env` block also sets the variables that common tools need in the sandbox. Each one answers a failure or a denial in a Shaders session:
	- `CI=true`, so pnpm relinks a cloned `node_modules` without asking for a TTY.
	- `TMP`, `TEMP`, and `TMPDIR`, all set to a short temp folder outside `~` that only this session uses. Claude Code's sandbox otherwise gives every session the same `TMPDIR`, where one Shaders check session overwrote another's log. turbo passes `TMP` to its tasks and drops `TMPDIR`. `srt` puts its proxy socket in the temp folder, and macOS caps a socket path at 104 bytes.
	- `TURBO_CACHE_DIR`, one per session. In a git worktree, turbo writes its cache to the main worktree, which is Flight Deck's clone.
	- `TURBO_ENV_MODE=loose`. turbo's strict mode drops `HTTPS_PROXY`, so a task that fetches skips the sandbox's proxy, and its DNS lookup fails.
	- `WATCHPACK_POLLING=true`. The sandbox blocks FSEvents, so `fs.watch` on a folder fails with `EMFILE`, and Next's dev server answered 404.
	- `NPM_CONFIG_USERCONFIG`, set to Flight Deck's own npm config. pnpm reads `~/.npmrc`, which can hold a registry token, and warns on every command when the sandbox denies it.
	- `NODE_OPTIONS`, which loads a script that retries a response the sandbox's proxy cuts short. `sandbox-runtime` closes the client's socket as soon as the upstream closes, so a download can end early with `ECONNRESET`, and Next's font download then never finished. The real fix belongs in `sandbox-runtime`.
- A sandboxed session can't write `.claude/settings.json` as a file, but it committed one through git plumbing in a test. A diff that touches `.claude/`, `.mcp.json`, the repo record, `CLAUDE.md`, or `AGENTS.md` pauses the issue before check, because check reads its instructions from the commit it judges.
- The dependency install is the session's first command, inside the sandbox. The runner first symlinks the repo's dependency folders out of the worktree, and it runs the dependency install itself only to refresh a dependency cache, under a sandbox with a session's limits (ADR 0018). The runner runs git with hooks off, as `git -c core.hooksPath=/dev/null`, so a hook that build added or edited, such as `.husky/pre-push`, never runs. Worktrees come from a clone that Flight Deck keeps for each repo (ADR 0015), so sessions can't move the maintainer's local refs. The runner works only in that clone, so it needs no Files and Folders grant for a repo under `~/Documents`.
- When the runner deletes a session's worktree (ADR 0002), it deletes the worktree's git metadata too. A daily sweep removes any worktree whose session no longer exists. Build's commits stay on the issue's branch in the clone. When a build session pauses, times out, or crashes, the runner keeps its commits there without pushing them, and the next build session starts from them. A pause for a rendered file is the one exception: the runner pushes build's commits so the maintainer can render the file on top of them (ADR 0022). Until the branch's first push, build may reset it to the base, such as after plan rewrites the brief. After that, build only adds commits, so every push stays a fast-forward.
- Before a session starts, the runner copies into its worktree only the gitignored files the repo record lists, such as `.env`, and setup recommends test credentials in them. Before the runner sends anything, it scans each diff, PR body, and comment for credential patterns and for the exact values of those files. The bundled Betterleaks, pinned at v1.9.0, matches the patterns through `betterleaks stdin`, and the exact-value check is the runner's own code. A hit pauses the issue. Sandboxed Bash can still read Keychain items, so the scan is the only backstop for them. In what goes to GitHub, the scan also catches absolute local paths and session IDs, and a hit there fails the outbox instead of pausing (ADR 0020).
- Setup adds its own ruleset on the default branch, `Flight Deck: require approval`, beside any the repo already has. It requires one approval, dismisses stale approvals on push, and blocks force pushes and deletion. Without the dismissal, the machine user could push after the maintainer approves and merge commits nobody approved. If the maintainer accepts setup's offer, the ruleset also requires `flight-deck/check` from any source, because GitHub pins a required status only to a GitHub App (ADR 0025). Factory branches get no rules.
- `flight-deck stop` holds the runner (ADR 0021), sends SIGTERM to every session, and pauses each session's issue with a comment that says the maintainer stopped it. The pause doesn't use up the stage's retry. SIGKILL would leave a session's background commands running. A session that hangs before its `init` event ignores SIGTERM, so `flight-deck stop` sends SIGKILL to any session still running 10 seconds later. The runner also kills a session that sends no `init` event within 2 minutes, pauses its issue without using up the stage's retry, and flags the maintainer. A macOS privacy prompt blocks a session that way until someone answers it. When the maintainer moves an issue out of its working status, the runner kills that issue's session at its next poll and discards the outbox. Pushed commits and an open PR stay. To resume, the maintainer moves the issue back into a factory queue, usually the one it left.
- When a session exits, the runner kills the process group of anything still running from its worktree or its dependency folders. A dev server that a session starts in the background runs in a process group of its own, outlives the session, and keeps its port. The sandbox denied the session's own `kill` on a server started with `&`. So sessions start the app with the Bash tool's `run_in_background` and a `timeout`, and stop it with `TaskStop`. The runner's kill at exit is the backstop.
- Nothing caps the issues the factory takes, because the maintainer sends each one. On a subscription, the runner holds itself short of the plan limits (ADR 0002). On an API key, the runner passes each session a budget with `--max-budget-usd` and holds itself at a daily cap and a monthly cap, so one bad day can't spend the month. `config.toml` holds the thresholds and caps (ADR 0015). Under the loop cap of 3, check pauses an issue instead of sending it back to build a third time, and a bot round that sends work back counts as a trip. A send-back from the maintainer starts a fresh count (ADR 0023).
