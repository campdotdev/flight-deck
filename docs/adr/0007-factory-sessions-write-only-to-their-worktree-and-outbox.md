# Factory sessions write only to their worktree and outbox

A factory session runs as the maintainer's macOS user, so it can reach the maintainer's own credentials. Sandboxed Bash read a Keychain item in a test, and the maintainer is on the ruleset's bypass list. A session that ran `git push origin main` with the maintainer's git login would get past the one approval that ADR 0005 made the hard stop. So no session holds a write credential. A session commits in its worktree and leaves an outbox: its handoff, its status move, and any PR body, media, or verdict. When the session exits, the runner checks the outbox against the stage's rules and makes every write in Linear and GitHub itself. Sessions get the Linear MCP server's read tools only and can't reach GitHub's hosts. Before check starts, the runner fetches what check needs from GitHub into the worktree. The runner never runs the repo's code outside a sandbox with a session's limits. These limits defend against mistakes and against instructions planted in text the factory reads, such as a stranger's comment on a public PR. They don't defend against code that escapes macOS's sandbox, and they don't apply to a flow the maintainer runs by hand.

## Considered options

- **Sessions write to Linear through the MCP server, behind a hook.** A `PreToolUse` hook would check each `save_issue` and `save_comment` call against the stage's allowed moves, and the runner would still make the GitHub writes. A session that died halfway would leave a handoff half posted.
- **Sessions hold the machine user's token,** as earlier tickets assumed, behind deny rules, hooks, and rulesets. Deny rules match command text, so `Bash(git push *)` doesn't stop `git -C . push`. A session could also skip the machine user and ask `git credential-osxkeychain` for the maintainer's token.
- **The sandbox runtime (`srt`) around the whole `claude` process.** It confines file tools, hooks, and MCP servers too, and the subscription login worked inside it in a test. It is a beta research preview at v0.0.80. It doesn't handle a worktree whose git folder lives elsewhere, and Claude Code's own Bash sandbox can't start inside it. It can replace the built-in sandbox later without changing anything else here.
- **Sessions run as a second macOS user** with its own Keychain. That closes the Keychain gap. It needs admin rights, a second Claude login, and repos that both users can read.

## Consequences

- The runner pushes fast-forward only, and only after a build session, so check never pushes and no session writes to a spec branch. The runner also opens and edits the PR, attaches media, sets `flight-deck/check`, marks the PR ready, posts comments, and moves statuses. Earlier tickets gave those writes to build and check, and those stages still decide them.
- The runner's own code enforces the lifecycle from ADR 0006. A stage moves its issue from its working status to its handoff status or to Paused. Plan may also mark its issue a duplicate of an open issue. Only the runner closes issues, in the three cases the lifecycle allows.
- A flow the maintainer runs by hand writes the same outbox and applies it with `flight-deck apply`, under the maintainer's own logins. The runner and hand runs share one write path.
- Every factory session runs in `dontAsk` with Claude Code's Bash sandbox on. `--settings` sets `allowUnsandboxedCommands: false` and `failIfUnavailable: true`, which makes the sandbox admin-required, so a repo's settings can't turn it off or loosen it.
- Sandboxed commands can't read under `~` except the paths the repo record reopens, and they reach only the hosts the record lists. `github.com`, `api.github.com`, and `uploads.github.com` are always denied. WebFetch runs outside the sandbox, so it gets the same host list plus documentation sites. Each extra MCP server exposes only the tools the record lists for it.
- Worktrees, dependency folders, and session temp folders live outside `~`, in a folder only the maintainer's user can open. A read under `~` fails with `EPERM`, not `ENOENT`, and many tools stop on `EPERM` when they look for a file in each folder above the working directory. With worktrees under `~`, Shaders' docs build failed when browserslist read `~/package.json`, and Next and webpack failed on `~/pnpm-lock.yaml` and `~/node_modules`.
- A trial denial under `~` doesn't mean setup reopens the path. turbo reads the Vercel CLI's login file, and reopening it would hand every session a credential. The runner points such a tool at an empty folder through the tool's own variable instead, such as `TURBO_CONFIG_DIR_PATH` and `VERCEL_CONFIG_DIR_PATH`. The repo record has no field for these variables, so each one is runner code.
- MCP servers run outside the sandbox. For a repo with a web app, the browser MCP server is the one process a session drives that can load pages, and a proxy contains it instead of the sandbox (ADR 0009). Chromium can't start from sandboxed Bash on macOS, so a repo's own browser tests run only in CI until the sandbox can start a browser.
- Sessions load the repo's `CLAUDE.md`, skills, and subagents, and nothing that runs code. The runner passes `--setting-sources project`, `disableAllHooks: true`, and `--strict-mcp-config`, and it turns off auto memory and the claude.ai connectors. A repo's `env` block outranks the process environment, so the runner sets every variable it depends on in the `env` block of `--settings`. This replaces ADR 0002's `project,local`, because in a worktree `local` loaded the maintainer's own approvals from the main checkout.
- `--setting-sources project` still loads `~/.claude/CLAUDE.md`, and `claudeMdExcludes` ignores a pattern that starts with `~`. So `--settings` excludes, by absolute path, `~/.claude/CLAUDE.md`, `~/.claude/rules/`, and every `CLAUDE.md`, `CLAUDE.local.md`, `.claude/CLAUDE.md`, and `.claude/rules/` in a folder above the worktree.
- Claude Code builds each session's shell snapshot by running the maintainer's shell startup file outside the sandbox, and it ignores `ZDOTDIR`. The runner sets `CLAUDE_CODE_SHELL=/bin/bash`, so a session gets `~/.bashrc`, which most Macs leave nearly empty, instead of `~/.zshrc`. Setup warns when `~/.bashrc` defines aliases or functions.
- The file tools ignore the sandbox, and a bare `Read` allow rule let a session read `~/.zshrc`. So allow rules for the file tools name only the worktree and the outbox, as `Read(//<path>/**)` and `Edit(//<path>/**)`, and `dontAsk` denies every other read. Two more folders get a `Read` rule, and the sandbox reopens both for reads. One is the installed version's skills, which flows read as files (ADR 0014). The other is the session's own folder under `~/.claude/projects/`, where Claude Code saves an MCP result too large to return inline and hands the session its path. A Figma page outline on Shaders ran to 358,475 characters, and without that rule `design-check` couldn't search it. The runner doesn't set `blockReadsOutsideWorkingDirectories`. On a Mac with a network mount under `~`, such as OrbStack's, that setting made macOS ask for Network Volumes access on the runner's behalf, and the session blocked until someone answered.
- `--settings` allows `Bash`. Without that rule, `dontAsk` denied sandboxed commands that used `$(...)`, a redirect, or an environment prefix. The sandbox is admin-required, so every command still runs sandboxed.
- Git exits when it can't read `~/.gitconfig`. The `env` block sets `GIT_CONFIG_GLOBAL` to Flight Deck's own git config, which holds the factory account's commit identity, and sets `GIT_CONFIG_NOSYSTEM=1`.
- The `env` block also sets the variables that common tools need in the sandbox. Each one answers a failure or a denial in a Shaders session:
	- `CI=true`, so pnpm relinks a cloned `node_modules` without asking for a TTY.
	- `TMP`, `TEMP`, and `TMPDIR`, all set to a short temp folder outside `~`. turbo passes `TMP` to its tasks and drops `TMPDIR`. `srt` puts its proxy socket in the temp folder, and macOS caps a socket path at 104 bytes.
	- `TURBO_CACHE_DIR`, one per session. In a git worktree, turbo writes its cache to the main worktree, which is Flight Deck's clone.
	- `TURBO_ENV_MODE=loose`. turbo's strict mode drops `HTTPS_PROXY`, so a task that fetches skips the sandbox's proxy, and its DNS lookup fails.
	- `WATCHPACK_POLLING=true`. The sandbox blocks FSEvents, so `fs.watch` on a folder fails with `EMFILE`, and Next's dev server answered 404.
	- `NPM_CONFIG_USERCONFIG`, set to Flight Deck's own npm config. pnpm reads `~/.npmrc`, which can hold a registry token, and warns on every command when the sandbox denies it.
	- `NODE_OPTIONS`, which loads a script that retries a response the sandbox's proxy cuts short. `sandbox-runtime` closes the client's socket as soon as the upstream closes, so a download can end early with `ECONNRESET`, and Next's font download then never finished. The real fix belongs in `sandbox-runtime`.
- A sandboxed session can't write `.claude/settings.json` as a file, but it committed one through git plumbing in a test. A diff that touches `.claude/`, `.mcp.json`, the repo record, `CLAUDE.md`, or `AGENTS.md` pauses the issue before check, because check reads its instructions from the commit it judges.
- The dependency install is the session's first command, inside the sandbox. The runner first symlinks the repo's dependency folders out of the worktree, and it runs the dependency install itself only to refresh a dependency cache, under a sandbox with a session's limits (ADR 0018). The runner runs git with hooks off. Worktrees come from a clone that Flight Deck keeps for each repo, so sessions can't move the maintainer's local refs.
- Before the runner sends anything, it scans each diff, PR body, and comment for credential patterns and for the exact values of the gitignored files it copied into the worktree. A hit pauses the issue. Sandboxed Bash can still read Keychain items, so the scan is the only backstop for them. In what goes to GitHub, the scan also catches absolute local paths and session IDs, and a hit there fails the outbox instead of pausing (ADR 0020).
- Setup's ruleset on the default branch requires one approval and blocks force pushes and deletion. Factory branches get no rules.
- `flight-deck stop` holds the runner (ADR 0021), sends SIGTERM to every session, and pauses each session's issue without using up the stage's retry. SIGKILL would leave a session's background commands running. A session that hangs before its `init` event ignores SIGTERM, so `flight-deck stop` sends SIGKILL to any session still running 10 seconds later. The runner also kills a session that sends no `init` event within 2 minutes, pauses its issue without using up the stage's retry, and flags the maintainer. A macOS privacy prompt blocks a session that way until someone answers it. When the maintainer moves an issue out of its working status, the runner kills that issue's session at its next poll and discards the outbox.
- When a session exits, the runner kills the process group of anything still running from its worktree or its dependency folders. A dev server that a session starts in the background runs in a process group of its own, outlives the session, and keeps its port. The sandbox denied the session's own `kill`.
- Nothing caps the issues the factory takes, because the maintainer sends each one. On an API key, the runner adds a daily cap to the monthly one. An issue that hasn't passed after its third verdict pauses.
