# Factory comments open with a status line, and a pause takes a one-word answer

Every handoff lives in Linear, as a comment the runner posts (ADR 0001, ADR 0007). In the FlutedGlass dry run on Shaders, the runner posted each session's file whole. A claims comment opened with a commit hash and a base, and the spec check's verdict ran to about 10,600 characters. A flag on the maintainer's phone read as the first words of a wall of text. So every factory comment now opens with a status line under 80 characters: a colored dot, a status phrase, and the gist. Three or four plain sentences for the maintainer come next, and the session's handoff sits below them in a fold titled `Details`. A flag assigns the maintainer first and posts its comment second, so the status line reaches the phone. A pause offers its answers as single words. When the maintainer's reply starts with one, the runner moves the issue to the status that answer names. A prototype posted five of the dry run's comments in this shape on scratch Shaders issues. The maintainer graded the notifications and the comments on their phone, and answered both test pauses with one word.

## Considered options

- **The handoff in a Markdown file attached to the issue.** Sessions read Linear only through the MCP server's read tools. `list_comments` returns a comment's whole body, fold included, but an attached file's contents sit at an `uploads.linear.app` URL that no session reads.
- **A Linear document for each handoff.** `get_document` can read one, but SHA-252 alone had nine handoffs, and each would add a document to the issue.
- **The handoff in a reply under the comment.** A reply is a second write, and on a flagged issue it sends the assignee a second push.
- **The handoff only in the runner's state folder.** The runner already copies build's latest claims and every verdict into the next session's inbox. Linear would lose the record the maintainer audits, and only the Mac that ran the session would keep it.
- **Comment first, then assign.** This was the prototype runner's order. Once the runner unsubscribes the maintainer (ADR 0011), a comment posted before the assignment reaches nobody, and the phone shows only "Flight Deck assigned you" and the issue's title.
- **Answer with a status move.** This was the old way: a comment, then a move to the status the pause's last line named. Two answers can send an issue to the same status, so the move alone can't carry the answer, and the maintainer made two writes.
- **Answer with an emoji reaction.** One tap carries only a yes, and SHA-252's pause needed "accept" or "rewrite".

## Consequences

- The runner writes the status line's dot and phrase from the session's status move, so the two always agree. 🟡 means the maintainer is needed: "Needs your answer", "Needs your help" for a step only they can do, "Needs your review", and "Needs your decision" for a proposal that debrief files (ADR 0012). 🟢 means the work moves on, as in "Moving to build", "Moving to check", "Passed check", "Marked duplicate" for a duplicate plan marks, and "Fixed" for a trouble cause that clears. 🔴 means "Back to build". On a default-branch failure's issue, which no stage works, "🔴 Failed again" marks a repeat failure and "🟢 Passed" the next pass (ADR 0013). ⚪ means paused without a flag, and only "Stopped" uses it, because a yellow dot would promise a flag that never came. The phrase follows what the maintainer has to do, not who raised the pause, so every pause the runner raises itself is "Needs your help": in each one, `retry` helps only after the maintainer acts. The status line carries no Markdown, because a phone shows it as plain text. For "Needs your review", the gist opens with the merge risk the runner computes from check's ratings (ADR 0020).
- Each stage's outbox gains `summary.md`: the gist on its first line, then about 400 characters for the maintainer. That part says what happened in the user's terms. It also names anything the maintainer would want to know when nothing needs them, such as a break, a skipped proof, or a shortcut, and for a flag it says what to do. It names issues by title and leaves out commit hashes, paths, rule citations, and session IDs. A sub-issue's pause also names its spec and the sub-issues it blocks. The flows ask for about 400 characters, and the runner accepts up to 600 after the first line. The fallback drops all of the prose, so a hard limit at 400 would throw away summaries that run a little long. If `summary.md` is missing, its first line pushes the status line past 79 characters, or the rest runs past 600, the runner writes a status line from the outcome alone and still posts the handoff in the fold, so prose never holds up the work.
- The `Details` fold holds the session's file as it stands, with the runner's footer, which names the session's stage. A follow-up issue's footer names the stage that filed it. A comment no session wrote has no handoff file, so its fold holds the runner's facts instead: the exit, the session ID, the attempt, the transcript path, and the last error message from the session's `result` event, after the secret scan. It never holds transcript text, which could carry a copied value. Its footer reads "Flight Deck <version> · runner". Paths and session IDs stay out of GitHub only (ADR 0020). Flows read each handoff from the fold. The runner still copies build's latest claims and every verdict into the next session's inbox.
- Linear's API stores a fold as a `+++ <title>` line and a closing `+++` line, but the MCP server shows it as `>>>`. So the runner writes `+++ Details` and `+++ Report`, and turns any `>>>` fold lines in plan's brief into `+++`.
- Each screenshot appears once, as an image embedded in the fold, or, for a brief, in the description, where the brief lives, while the fold names the file. Linear stores plain upload URLs, and the MCP server signs each one as it returns it, with a 5-minute expiry. So a session names a screenshot by its file and never copies an upload URL. The runner uploads and embeds the screenshots of every file it posts, not only `verdict.md`, and it strips any `?signature=` it finds. Each upload uses Linear's `fileUpload` mutation.
- A flag sends two notifications: "assigned to you", which shows the issue's title, and then the comment. The maintainer graded the result as reading much better and didn't ask to cut either one.
- A pause offers up to three answers. Each one is a single word, says what happens next, and names the status the issue moves to. Some pauses offer only one, such as `retry` after a failed CI audit (ADR 0025). Two of plan's pauses offer none, because no one-word answer settles them: code that already does what the report asks, which the maintainer closes, and an issue too big for one build, which the maintainer splits (ADR 0026). Their comment leaves out the answer lines and says what to do. The pause's `outcome.json` lists them in `answers`, each with its word, what happens, and its status, so the comment and the runner use the same words. The comment lists the answers after the part for the maintainer, one line each, with the word in bold and what it does. A line after them says that any other reply leaves the issue paused until the maintainer moves it. A pause whose cases lead to different statuses offers whole answers, so one word decides the status. On SHA-252, "rewrite" also meant "continue".
- The runner gains one move: from Paused to the status an answer names. It makes the move when a comment the maintainer posts after the pause starts with that answer, ignoring case and trailing punctuation. It then clears the flag. Any other reply leaves the issue paused and flagged until the maintainer moves it. Either way, the next session reads the whole reply, so an answer can carry context after its first word. The runner's code enforces this move with the rest of the lifecycle (ADR 0007).
- The runner's own comments come from fixed texts in its code, with no model call, and each pause ends with the same answer lines as a session's. Plan is the example stage:
	- A second failed session (ADR 0002): "🟡 Needs your help: plan failed twice". The text names the second exit in plain words, such as "ran past plan's 30-minute limit", "stopped with an error", "wrote a handoff Flight Deck refused, because <the rule>", or "couldn't start, because Flight Deck couldn't prepare its worktree", and says the transcript's path is under Details. It offers `retry`, which restores the stage's retry.
	- A session that sent no `init` (ADR 0007): "🟡 Needs your help: plan's session never started". It says a prompt on the Mac is the usual cause and asks the maintainer to dismiss any dialog from macOS or Claude Code. It offers `retry`.
	- The record pauses (ADRs 0003, 0015, and 0017): "this repo has no Flight Deck record yet", which asks for `/flight-setup` and a merged record; "this repo's Flight Deck record has an error", which quotes the first error and puts the rest under Details; and "this repo's record needs a newer Flight Deck", which names both schemas and asks for `flight-deck update`. Each names the repo's real default branch and offers `retry`.
	- A secret-scan hit (ADR 0007): "🟡 Needs your help: plan's handoff held what looks like a secret". It names the file and the rule, or the key whose value matched, such as `STRIPE_KEY` from `.env`, never the value. It says that nothing left the Mac, and invites a reply that tells plan what to leave out. It offers `retry`, the same word as every other pause the runner raises.
	- A canceled blocker (ADR 0004): "🟡 Needs your help: a blocker was canceled", or "a blocker is a duplicate of nothing". The text links the blocker by title, because a long title would push the status line past 79 characters, and asks the maintainer to remove the relation or reopen the blocker. It offers `retry`.
	- A single-instance app's port in use (ADR 0003): "🟡 Needs your help: port <port> is in use". It asks the maintainer to stop whatever else uses the port, such as their own dev server, and offers `retry`.
	- An apply that couldn't write to Linear for 3 hours (ADR 0002): "🟡 Needs your help: Flight Deck couldn't write to Linear". It says the stage finished and its handoff is kept, and offers `retry`, after which the next take writes the kept handoff without a new session.
	- `flight-deck stop` (ADR 0007): "⚪ Stopped: you stopped Flight Deck while plan ran". It flags nothing and offers `retry`, which moves the issue back to its stage's queue, so the maintainer can answer it with one word when they get to it.
	- A stale take (ADR 0011): "🟡 Needs your help: in Planning for 3 hours with no Flight Deck session". The issue isn't paused, so it offers no answer. It says to finish the hand run, or to move the issue back to its queue so the factory takes it.
	- A duplicate is plan's own outbox, with its own `summary.md`. Under it, the runner adds one line that links the original by title, so the link survives a fallback.
- A trouble issue (ADR 0011) opens with no comment, because the phone shows "assigned to you" and the title. So the title takes the status line's place. It is plain text shaped "<what broke>: <the fix>", such as "Flight Deck can't sign in to GitHub: run flight-deck login github". A title stays whole when a long workspace or status name pushes it past 79 characters. The body says what stopped, where, and since when, gives the fix as numbered steps, and ends "Flight Deck comments here once it works again. Close the issue then." Its fold holds the cause and the error the runner saw. When the cause clears, the runner comments "🟢 Fixed: " and what works again, such as "Flight Deck can sign in to GitHub again", with one sentence on what restarts. The titles:
	- `claude_login`: "Claude Code's login expired: run claude, then /login".
	- `claude_login_soon`: "Claude Code's login expires soon: run claude, then /login".
	- `claude_code_version`: "Claude Code 2.1.0 is too old for Flight Deck: run claude update", with the real version.
	- `github_token`: "Flight Deck can't sign in to GitHub: run flight-deck login github".
	- `linear_login`: "No Linear login for <workspace>: run flight-deck login linear <workspace>".
	- `missing_status`: "Linear status <name> is missing: rename it back or rerun setup".
	- `linear_token`: "Flight Deck couldn't get a Linear token for <duration>", such as "for 3 hours", in the past tense, because the runner files it only once a mint works again (ADR 0005). Its body names the four causes that look alike from the Mac and what to check if it happens again. It gets no cleared comment.
	- `debrief_failed`: "Flight Deck's debrief failed twice: close this issue to run it again", "Flight Deck's debrief never started: close this issue to run it again", or "Flight Deck couldn't file debrief's proposals: close this issue to run it again" (ADR 0012). The maintainer clears it by closing the issue, so it gets no cleared comment.
	- `credentials` files no issue. Its macOS notification reads "Flight Deck stopped: others can read credentials.env. Run chmod 600 on it." Every other cause's notification, titled "Flight Deck", repeats its issue's title, except one: when a Linear mint first fails, no issue exists yet, so the notification reads "Flight Deck can't get a Linear token for <workspace>. It keeps trying." A cause the runner can't file as an issue, such as `linear_login`, gets only its notification, worded like a title.
- Answering means opening the issue, which marks the flag read. So clearing the flag sends "Flight Deck unassigned you" (ADR 0011).
